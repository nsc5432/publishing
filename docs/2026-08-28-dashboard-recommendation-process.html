한 번의 SQL로 받은 원시 슬롯을 상위 시설코드로 갈라 두 벌의 집계를 만든다. 카드 제목·수치는 기존 표시 범위를 유지하고, 추천 계산만 좁은 범위를 쓴다. 혼잡등급 기준표(TN_PM_PSG_PRCS_GRD)도 추천 범위의 시설 그룹으로 조회한다.

곡선 모양은 피크 위치를 보여 주기 위한 예시다. 실제로는 CAST 결과 슬롯을 그대로 쓴다.

식 — 줄별 주석

// 피크까지의 시간 동안 시설 1대가 처리하는 총 인원. 나눗셈의 분모가 된다.
// 구간 전체(60분)가 아니라 leadMinutes 인 것이 핵심 — 피크 순간에 이미 NORMAL 이어야 한다.
capacityPerFacility = μ · leadMinutes

// 피크에서 걷어내야 하는 인원. 0 이하면 이미 원활이라 증설이 필요 없다.
excess = max(0, peakQueue − target)

// 피크 시점에 target 이하가 되게 하는 최소 정수 추가 대수.
//   peakQueue − extra·μ·lead ≤ target  ⟺  extra ≥ excess / (μ·lead)
// 부등식의 최소 정수해가 곧 ceil 이다.
extraCnt = ceil(excess / capacityPerFacility)

// CAST 곡선은 이미 currentOpenCount 의 처리가 반영된 잔여 큐다.
// 그래서 이 식이 내는 값은 자연히 "추가" 이고, 총 소요는 현재 운영 수를 더한 값이다.
reqCnt = currentOpenCount + extraCnt

// 역검증 — 구한 대수를 되넣어 피크가 정말 목표 이하인지 확인한다.
predictedPeakQueue = max(0, peakQueue − capacityPerFacility · extraCnt)

// 혼잡해소: 곡선을 extraCnt 만큼 보정해 target 아래로 처음 내려가는 슬롯을 찾는다.
// 보정에 쓰는 값은 reqCnt 가 아니라 extraCnt 다 — 곡선에 현재 운영분이 이미 들어 있다.
// peakAt 에서 반드시 성립하므로 해는 항상 존재하고 endDt 를 넘지 않는다.
cgnClearTime = bgnDt + min{ t | queue(t) − extraCnt · μ · t ≤ target }

기본값으로 따라가 보기

peakQueue = 1118 @ +60분 · μ = 0.42 · target = 420 · currentOpenCount = 12

capacityPerFacility = 0.42 × 60          = 25.2 명/시설
excess              = 1118 − 420         = 698 명
extraCnt            = ceil(698 / 25.2)   = ceil(27.70) = 28 개
predictedPeak(28)   = 1118 − 28 × 25.2   = 412 ≤ 420   // 검증 통과, 여유 8명
predictedPeak(27)   = 1118 − 27 × 25.2   = 438 > 420   // 27 개로는 미달 → 28 이 최소
reqCnt              = 12 + 28            = 40 개

종전 식과 같은 답이 나오는 이유

큐가 단조 증가해 피크가 구간 끝에 오는 경우, CAST 곡선의 마지막 값은 정의상 peak = q(H) = Q0 + A − open·μ·H 다. 이걸 넣으면 

reqCnt = open + ceil((peak − target) / (μH))
       = open + ceil((Q0 + A − target)/(μH) − open)
       = open + ceil((Q0 + A − target)/(μH)) − open     // ceil(x−정수) = ceil(x)−정수
       = ceil((Q0 + A − target) / (μH))                 // 유입량을 쓰던 종전 식

두 방식은 대수적으로 동일하다. 유입량 A 역산은 CAST 곡선에서 뽑아낸 값으로 그 곡선을 다시 재구성하는 우회였다. 차이가 생기는 건 피크가 구간 중간에 있을 때뿐이고, 그때는 새 식이 피크 순간을 기준으로 잡아 더 안전측으로 나온다.

왜 두 예외는 정상 입력에서 안 터지는가

extraCnt ≥ excess/(μ·lead) 이므로 양변에 μ·lead 를 곱하면 extraCnt·μ·lead ≥ excess 이고, 따라서 predictedPeakQueue ≤ target 이 항상 성립한다 — “피크를 목표 이하로 낮출 수 없다” 예외는 도달할 수 없다. 같은 부등식이 t = leadMinutes 에서 보정 곡선이 target 이하임을 보장하므로 “해소 시각을 찾을 수 없다” 도 마찬가지다.

즉 이 두 검사는 방어 코드가 아니라 입력 집계·반올림 오류 탐지기다. 걸렸다면 peakQueue·leadMinutes·μ 중 하나가 산식이 기대하는 의미와 다르게 집계됐다는 뜻이므로, 수량을 보정하지 말고 입력 요약과 함께 실패시킨다.

이번 변경으로 없어진 것

유입량 역산(getForecastArrivals()) 전체, 자정 구간에서 종료 스냅샷을 요구하던 검사, 10분 간격 단정, max(0, …) 의 상향 편향. processed 를 더 이상 쓰지 않으므로 SMLT_ACTL_DT 가 구간 시작인지 종료인지 확정하지 않아도 된다.

구현상의 주의

중간 계산은 BigDecimal(DECIMAL128)로 하고 마지막 수량에서만 RoundingMode.CEILING 을 쓴다. double 로 하면 나눗셈 결과가 28.000000000000004 처럼 떠서 필요 없는 1개가 더 붙는다. extraCnt 는 ceil 때문에 항상 [0, μ·lead) 만큼의 여유 용량을 갖는다.

reqCnt(옛 addCnt)는 총 소요 수량이고 물리적 보유 대수를 넘어도 clamp 하지 않는다. 실행 가능 수량이 아니라 “현재 수요와 처리능력이 요구하는 양” 을 그대로 보여 주는 값이기 때문이다.

모델의 한계 — 읽을 때 감안할 것

① 시설을 늘리면 큐 곡선 자체가 달라지는데 선형 보정으로 근사한다. ② μ 는 관측 실적에서 나온 값이라 대당 처리 속도가 유지된다는 선형 확장 가정이 깔려 있다. ③ 피크 한 점이 기준이라 짧은 스파이크 하나에도 수량이 뛴다 — 총량 기반이던 종전 식은 스파이크를 평균화했다. ④ currentOpenCount 가 수량에 직접 들어가므로 운영 수 조회의 정확도가 곧 추천의 정확도다. ⑤ 해소 시각은 결과 슬롯 해상도인 10분 단위로만 나온다.
