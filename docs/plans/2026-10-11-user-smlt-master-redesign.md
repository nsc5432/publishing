# 사용자 시뮬레이션 현재상태 분리 및 공통 실행 마스터 재설계

작성일: 2026-10-11
대상: react/src, java/cast, java/castrest, java/mapper, java/ddl, AGENTS.md
문서 성격: 인터뷰에서 확정한 정책에 따른 수정 요청 및 구현 계획. 이 문서 작성으로 코드·DB를 변경하지 않는다.

## 1. 수정 목적

현재상태 저장에 기존 결과의 SMLT_ID를 사용하는 구조를 없앤다.
현재상태는 사용자·대상 일자·터미널별로 관리하고, SMLT_ID는 시뮬레이션 실행 1건을 식별한다.
일일·사용자 시뮬레이션에 공통 실행 마스터를 두고 요청·수행이력·결과를 같은 SMLT_ID로 연결한다.

## 2. 인터뷰 확정사항

| 항목 | 확정 정책 |
|---|---|
| 현재상태 소유 범위 | 사용자별 독립 관리 |
| 현재상태 일자 범위 | 대상 일자별 저장 |
| 터미널 범위 | 현재상태는 터미널별 관리, 실행은 T1·T2 전체 |
| 저장된 조건이 없는 경우 | 해당 날짜의 운영자료로 채움. 여객 조정률은 0% |
| 실행 전 미저장 변경 | 자동 저장 후 실행 |
| 열거나 저장하지 않은 영역 | 기존 저장 조건을 우선 사용하고, 없으면 해당 날짜 운영자료 사용 |
| SMLT_ID 채번 범위 | 일일·사용자 시뮬레이션 전체 공통 MAX + 1 |
| 사용자 SMLT_ID 발급 시점 | 사용자 시뮬레이션 실행 요청 시 |
| 일일 SMLT_ID 발급 시점 | CAST 결과 수신 시 |
| 요청·이력·결과의 ID | 같은 SMLT_ID 사용 |
| 공통 실행 마스터 | 별도 테이블 생성 |
| 실행 중 추가 요청 | 허용. 매 요청에 새 SMLT_ID 발급 |
| 실행이력·결과 조회 | 조회 권한이 있는 모든 사용자에게 공개 |
| 수행 회차 | SMLT_FLFMT_SN / smltFlfmtSn 제거 |
| 기존 데이터 | 조건·수행이력·결과를 보존하고 이관 |
| 기존 조건의 소유자 | 최초 저장자 |
| 같은 소유자·일자·터미널·영역의 이관 후보 | 기존 SMLT_ID가 가장 큰 조건을 현재상태로 선택 |
| 선택되지 않은 기존 조건 | 이관 원본·기록으로 보존 |

현재상태의 사용자별 분리와 실행이력·결과의 공개 범위는 서로 다른 정책이다.
타인의 현재상태를 조회·수정하지 못하게 하고, 공개 결과의 조건 조회는 실행 당시 확정 조건을 읽는다.

## 3. 현재 구현에서 바꿀 부분

- CastUserSmltServiceImpl.retrieveUserSmltInfo는 해당 일자의 사용자 결과 ID, 없으면 일일 결과 ID를 선택해 편집 키로 반환한다.
- 운항·체크인·출국장 현재상태 테이블은 SMLT_ID를 PK에 포함하고 조회·저장·삭제 조건으로 사용한다.
- executeUserSmlt는 전달받은 기존 SMLT_ID를 재사용하고 SMLT_FLFMT_SN만 증가시킨다.
- 실행 대상 일자 및 기본 리소스를 기존 TN_PM_SMLT_STNG 조회에 의존한다.
- 모든 조건을 미리 저장해야 실행할 수 있고, 실행 중 요청이 있으면 추가 실행을 차단한다.
- 프런트 실행 버튼에는 전체 편집 상태를 모아 자동 저장하는 흐름이 없다. 탭별 로컬 상태와 save.ts의 void 반환도 수정 대상이다.
- CastRestServiceImpl.insertResult는 결과 수신 시 항상 SQ1_TN_PM_SMLT_RSLT.NEXTVAL로 새 ID를 만든 뒤 TN_PM_SMLT_STNG를 입력한다.
- 현재 확인된 코드에서는 사용자 요청과 결과를 연결하는 retrieveUserReq / closeUserReq 호출이 주석 처리되어 있다.
- TN_PM_SMLT_STNG의 PK는 (SMLT_ID, SMLT_MDL_SN)이다. 공통 실행 1건의 마스터와 모델별 설정 정보를 분리한다.
- 리소스 번호의 002~999 순환 재사용과 FS 번호만으로 요청을 찾는 방식은 추가 실행 허용·과거 실행 보존 정책과 함께 검토해야 한다.

## 4. 목표 데이터 구조

### 4.1 공통 실행 마스터 신설

새 테이블명은 TN_PM_SMLT_MSTR를 제안한다.
아래 컬럼명·자료형은 구현 초안이며, 실제 스키마와 표준단어·기존 코드 체계를 대조해 확정한다.

| 컬럼 초안 | 역할 |
|---|---|
| SMLT_ID | 실행 1건의 PK. 기존 8자리 ID와의 호환성 및 최대값 확인 |
| SMLT_TYPE | 일일·사용자 등 기존 시뮬레이션 유형 코드 |
| EXCN_YMD | 시뮬레이션 대상 일자. 요청한 날짜와 구분 |
| SMLT_STTS | 실행 상태. CAST 상태 및 화면 상태와의 매핑 정의 |
| SMLT_REQ_DT | 사용자 실행 요청 시각. 일일은 확인되지 않은 요청 시각을 임의 생성하지 않음 |
| SMLT_BGNG_DT | 실제 수행 시작 시각. CAST에서 확인 가능한 값 사용 |
| SMLT_END_DT | 실제 수행 종료 시각 |
| FRST_RGTR_ID | 사용자 실행 요청자 또는 기존 일일 수신 등록 주체 |
| FRST_REG_DT 등 감사 컬럼 | 마스터 등록·수정 감사 정보 |

- 실행 마스터에는 터미널별 행을 만들지 않는다. 사용자 요청 1건이 T1·T2 전체를 포함한다.
- TN_PM_SMLT_STNG는 SMLT_ID로 마스터를 참조하는 모델·터미널·입력 리소스 등의 설정 정보로 유지한다.
- TN_PM_SMLT_RSLT_DTL 등 결과 테이블도 동일한 SMLT_ID를 사용한다.
- TN_PM_SMLT_USER_MSTR의 사용자 실행 요청은 공통 마스터를 참조한다.
- TH_PM_SMLT_FLFMT_HSTRY는 회차 축을 제거하고 실행 SMLT_ID 기준으로 관리한다. 기존 이력 상세는 보존한다.
- 요청 상태 New / Executing / Finished / Failed와 화면 RUNNING / DONE / FAILED의 기존 매핑을 유지한다.
- 일일 마스터는 결과 저장 성공 시 완료 상태로 생성한다. 수신 전의 요청·진행 상태를 추정해 넣지 않는다.
- MASTER와 STNG 사이의 FK, 결과 테이블 FK, 사용자 요청 FK를 실제 PK 구조에 맞춰 정의한다.
- 사용자 결과를 별도 RSLT_SMLT_ID로 다시 채번하는 구조는 제거한다. 호환 목적의 기존 컬럼이 필요한 기간에는 같은 SMLT_ID를 가리키도록 정리한다.

### 4.2 현재상태 저장 키 변경

현재상태의 논리 키를 (사용자 ID, 대상 일자, 터미널)로 바꾼다.
소유자 컬럼은 감사용 FRST_RGTR_ID와 별도로 둔다. 사용자 ID는 세션에서 얻고 요청 본문 값을 신뢰하지 않는다.

| 테이블 | 새 키의 추가 축 |
|---|---|
| TN_PM_SMLT_USER_FLT_PSG_AJMT | 사용자·일자·터미널 |
| TN_PM_SMLT_USER_CHKN_ISL | 사용자·일자·터미널·아일랜드 |
| TN_PM_SMLT_USER_CHKN_OPER_HR | 부모 키·운영시간 구간 |
| TN_PM_SMLT_USER_CHKN_BOOTH | 부모 키·부스 및 기존 배정 식별 축 |
| TN_PM_SMLT_USER_DPTGT | 사용자·일자·터미널·출국장 |
| TN_PM_SMLT_USER_DPTGT_OPER_HR | 부모 키·운영시간 구간 |
| TN_PM_SMLT_SCSH_OPER_PLAN | 사용자·일자·터미널·출국장·시간대 등 기존 식별 축 |

- 기존 시설·시간·부스 식별 키는 임의로 축소하지 않는다.
- 체크인·출국장의 전체 교체 저장 방식은 유지하되 삭제 범위를 사용자·일자·터미널로 제한한다.
- 저장 시각 및 저장 여부도 같은 범위로 조회한다.
- 현재상태 조회·저장에 SMLT_ID를 요구하지 않는다.
- 원본 운영자료 및 비교 지표에 필요한 기준 결과 ID는 편집 키와 분리한다.
- 기존 USER 결과 ID를 조회하거나 DAILY 결과 ID로 fallback하는 편집 대상 결정 로직은 제거한다.
- 해당 일자의 기존 시뮬레이션 결과가 없다는 이유만으로 현재상태 조회·저장을 막지 않는다.
- 운영자료 자체가 없는 경우는 빈 자료와 조회 오류를 구분한다. 실행에 필요한 자료가 없으면 누락 내용을 알리고 실행 등록을 완료하지 않는다.

### 4.3 실행 당시 조건 보존

- 사용자 실행마다 당시 확정 조건을 SMLT_ID에 연결해 보존한다.
- 이후 현재상태를 수정하거나 다른 실행을 등록해도 기존 실행 조건·입력 리소스가 바뀌면 안 된다.
- 보존 대상은 두 터미널의 운항 조정률·체크인 설정·출국장 설정과 실행에 사용한 입력 리소스이다.
- 모니터링의 조건 조회 및 mode=view&smltId 진입은 이 확정 조건을 읽는다.
- 순환 CAST 리소스 테이블만으로 과거 조건 보존을 대신하지 않는다. 재사용되는 전송용 리소스와 실행별 보존 자료를 구분한다.

## 5. 목표 처리 흐름

### 5.1 현재상태 조회·수동 저장

1. 세션 사용자와 화면의 대상 일자·터미널을 확정한다.
2. 그 범위에 저장된 조건이 있으면 반환한다.
3. 저장되지 않은 영역은 해당 날짜 운영자료를 기본값으로 반환한다.
4. 사용자가 저장하면 같은 키에 반영한다. SMLT_ID나 수행이력을 만들지 않는다.
5. 탭별 수동 저장은 유지하고, 다른 사용자·일자·터미널의 행을 건드리지 않는다.

### 5.2 사용자 실행

1. 두 터미널·세 영역의 미저장 편집 내용을 모은다.
2. 세션 사용자와 대상 일자를 기준으로 기존 저장 조건을 읽는다.
3. 실제 수정한 영역은 전달된 편집 내용으로 자동 저장한다.
4. 열지 않은 영역은 기존 저장 조건을 우선 사용하고, 없는 영역만 운영자료로 채운다.
5. 두 터미널의 최종 조건을 검증한다.
6. 공통 채번 경로에서 새 SMLT_ID를 발급하고 마스터를 생성한다.
7. 확정 조건과 불변 CAST 입력 리소스를 생성한다.
8. 같은 SMLT_ID로 수행이력 및 New 상태의 사용자 실행 요청을 등록한다.
9. 새 SMLT_ID와 상태를 응답한다. 이미 진행 중인 다른 실행 때문에 거절하지 않는다.

구현 제안: 자동 저장·기본값 확정·ID 발급·스냅샷·마스터·이력·요청 등록은 서버의 실행 API에서 한 트랜잭션으로 처리한다.
프런트가 여러 저장 API를 순차 호출하고 실패 여부와 무관하게 실행하는 방식은 피한다.
단일 실행 등록 실패 시 일부 조건만 저장되거나 마스터·리소스만 남지 않도록 롤백한다.
일반 탭별 수동 저장까지 하나의 API로 합치는 것은 요구사항이 아니다.

### 5.3 CAST 상태 및 결과 수신

- 외부 CAST의 polling 및 상태 통보 구조를 유지한다. 서버 선점 처리나 신규 스케줄러를 추가하지 않는다.
- 사용자 결과는 실행 요청을 확정적으로 식별한 다음 그 요청의 SMLT_ID를 재사용한다.
- 일일 결과는 공통 채번 경로에서 SMLT_ID를 발급하고 마스터·설정·상세 결과를 함께 생성한다.
- 결과 수신 경로에서 사용자 결과에 새 SMLT_ID를 발급하지 않는다.
- 같은 실행에 속한 모델·터미널 결과는 같은 SMLT_ID 아래에 저장한다. 실제 CAST 결과 묶음 단위를 확인한다.
- 요청·실행 ID가 CAST와 어떻게 왕복하는지 기존 프로토콜로 확인한다. 결과에 존재하지 않는 필드를 있다고 가정하지 않는다.
- SMLT_REQ_ID / WhatIfRunID가 외부 계약상 필요한 경우 프로토콜 식별자로 유지할 수 있으나, 내부 실행은 SMLT_ID 하나로 식별한다.
- FS 리소스 번호만으로 단일 요청을 찾는 기존 방식은 순환 재사용 시에도 유일한지 검증한다.
- 매칭이 불가능하거나 중복되는 경우 가장 최근 요청에 임의 연결하지 않는다. 원문과 미연결 상태를 보존하고 원인을 드러낸다.
- 사용자 요청 매칭·완료 처리의 주석 처리된 경로를 새 구조에 맞춰 복구한다.
- 결과 저장과 마스터·수행이력·요청의 완료 갱신을 한 트랜잭션으로 처리한다.
- 같은 결과를 다시 받아도 마스터·상세 결과·완료 처리가 중복되지 않도록 원천 결과 식별 기준을 둔다.

### 5.4 공통 MAX + 1 채번 및 추가 실행

- 사용자 실행 등록과 일일 결과 수신이 같은 채번 함수를 사용한다.
- MAX는 완료 결과만이 아니라 결과가 없는 요청·실행 중 마스터까지 포함한다.
- 이관 후의 기존 ID 상한과 충돌하지 않아야 한다. 기존 Manual 등 다른 유형 ID도 기존 데이터로 보존한다.
- 독립적인 SQ1_TN_PM_SMLT_RSLT.NEXTVAL 사용을 남겨 공통 번호와 충돌하게 하지 않는다.
- MAX 조회 후 INSERT를 잠금 없이 수행하지 않는다. 고정 잠금 행 SELECT FOR UPDATE 등 DB 직렬화 방식과 PK 제약을 함께 사용한다.
- 요청이 동시에 들어오더라도 서로 다른 ID를 받아야 한다. 채번 충돌을 실행 중 중복 요청 메시지로 처리하지 않는다.
- 같은 사용자·날짜의 동시 자동 저장과 스냅샷 발행도 서로 다른 편집 상태가 섞이지 않게 직렬화 또는 동등한 일관성 제어를 적용한다.
- ID 자료형·숫자 변환·최대 자릿수·빈 테이블의 시작값은 실데이터와 기존 ID 형식을 확인해 명시한다.
- retrieveActiveReqCnt에 의한 추가 실행 차단 및 그 정책을 강제하는 UX_ACTIVE 제약은 제거·변경한다.
- CAST 리소스 번호 002~999의 현재 계약은 별도 실행 ID와 구분한다.
- 활성 실행이 사용하는 번호를 덮어쓰지 않는다. 전송용 번호를 재사용해도 과거 실행 스냅샷과 결과 매칭 근거는 보존한다.
- 가용 리소스 번호 부족 시 기존 실행을 덮어쓰지 말고 등록을 실패시킨다. 장기 보존과 번호 재사용 방안은 구현 설계에서 명시한다.

## 6. 프런트 및 API 수정 요청

- 현재상태 조회·저장 DTO를 대상 일자·터미널 기반으로 변경한다. 사용자 소유 범위는 서버 세션으로 결정한다.
- 현재상태 저장 요청에서 smltId를 제거하고, 실행 응답·결과 조회의 smltId는 유지한다.
- 실행 요청은 대상 일자와 미저장 변경 영역을 전달하도록 설계한다.
- 모든 수정 영역을 수집할 수 있도록 폼 상태를 페이지 또는 공용 상태 계층에서 관리한다.
- T1·T2 전환이나 탭 이동으로 미저장 내용이 사라지지 않게 한다. 열지 않은 영역을 빈 배열이나 기본값으로 잘못 덮어쓰지 않는다.
- save.ts 및 저장 호출의 완료·실패를 호출자가 판단할 수 있게 한다. 실패를 내부 catch로 삼키고 실행 성공으로 진행하지 않는다.
- 자동 저장·실행 등록 성공 시 변경 상태와 저장 시각을 갱신하고 새 smltId를 반영한다.
- 기존 실행의 RUNNING 상태를 이유로 새 실행 버튼을 막지 않는다. 현재 HTTP 요청 처리 중의 중복 클릭 제어는 별도로 둔다.
- 상태 표시는 최신 1건으로 과거 실행을 덮는 데이터 모델을 만들지 않고 실행별 이력을 유지한다.
- 모니터링에서 smltFlfmtSn 의존을 제거하고 smltId로 상세·조건·결과를 조회한다.
- 결과의 공개 조회에 현재상태 소유자 필터를 잘못 적용하지 않는다.
- 목업도 사용자·일자별 현재상태, 자동 저장, 새 ID, 다중 실행, 공용 결과 정책과 일치시킨다.

기존 DTO 필드명을 단순 리네임하지 않는다.
이 요청에 필요한 smltId의 현재상태 요청 제거, smltFlfmtSn 제거 및 신규 필드 추가는 명시적인 API 계약 변경으로 문서화하고 프런트·백엔드를 함께 수정한다.
enum 문자열, className, DOM id, CSS 토큰 및 이번 요청과 무관한 DTO 필드는 유지한다.

## 8. 기존 데이터 보존 및 이관

1. 실제 DB의 컬럼·PK·FK·인덱스·시퀀스·코드값을 조회해 참조 DDL과 대조한다.
   이 저장소의 사진 판독 DDL만으로 운영 스키마를 확정하지 않는다.
2. 이관 전 원본 데이터와 제약 정의를 보존한다. 신구 식별자 대응표와 실행별 이관 결과를 남긴다.
3. 기존 조건의 소유자는 각 저장 영역의 최초 저장자 FRST_RGTR_ID를 기준으로 한다.
   대상 일자는 기존 SMLT_ID가 가리키는 설정 정보와 대조한다.
4. 같은 소유자·일자·터미널·영역의 후보 중 기존 SMLT_ID가 가장 큰 저장 묶음을 현재상태로 선택한다.
   체크인·출국장은 부모와 자식 전체를 같은 기존 SMLT_ID에서 가져오고 서로 다른 후보의 행을 섞지 않는다.
5. 선택되지 않은 기존 조건도 원본 보관 및 이관 대응표에 남긴다.
6. 소유자·대상 일자가 없거나 후보의 숫자 ID 형식이 잘못된 행은 임의 사용자·일자에 배정하지 않는다.
   원본을 보존하고 미확정 목록·사유를 생성해 이관 완료 전 해결한다.
7. 기존 결과 SMLT_ID는 가능한 한 유지하면서 공통 마스터를 생성한다.
   여러 모델·터미널 설정 행의 SMLT_ID가 같으면 같은 실행으로 묶되, 실제 데이터의 의미를 확인한다.
8. 기존 사용자 요청·회차 이력은 실행 1건씩 분리한다.
   결과가 연결된 요청은 해당 기존 결과 ID와 통합하고, 결과가 없는 요청에는 충돌 없는 새 공통 ID를 부여한다.
9. 구 (SMLT_ID, SMLT_FLFMT_SN, SMLT_REQ_ID, RSLT_SMLT_ID)와 신 SMLT_ID의 대응표를 보존한다.
   공개 코드에서 회차를 제거하더라도 원래 회차 값은 이관 감사 자료에서 잃지 않는다.
10. 연계가 불명확한 이력은 기존 ID가 같다는 이유만으로 하나의 실행에 합치지 않는다.
    기존 운영자료 참조 및 리소스 정보로 연결을 검증하고, 복원할 수 없는 부분은 미확정 상태로 보존한다.
11. 진행 중인 요청의 WhatIfRunID·입력 리소스를 바꾸어 CAST가 다른 요청으로 인식하게 하지 않는다.
    적용 시점에 진행 중 요청을 완료시키거나 기존 식별자를 지원하는 호환 매핑을 둔다.
12. 마스터·요청·이력·설정·상세 결과의 건수, FK, 합계, 소유 범위와 대응표의 누락 여부를 검증한다.
13. 새 구조 검증 후 구 키·회차·추가 실행 차단 제약을 단계적으로 제거한다.
    보존 자료까지 삭제하는 초기화 SQL을 이관 절차에 넣지 않는다.
14. 이관 SQL의 재실행 시 중복 생성 방지, 적용 순서, 실패 시 복구 절차를 함께 작성한다.

## 10. 검증 및 완료 기준

### 저장 및 기본값

- 같은 날짜라도 사용자 A와 B의 현재상태가 분리되고, 다른 날짜·터미널에 저장이 번지지 않는다.
- 과거 결과가 없는 날짜도 운영자료가 있으면 조회·저장할 수 있다.
- 저장 없는 영역은 운영자료, 운항 조정률은 0%로 표시한다.
- 다른 사용자의 편집 키를 조작해도 조회·저장되지 않는다.

### 자동 저장 및 실행

- T1 일부만 수정해 바로 실행해도 미저장 변경, T2 기존 저장 조건, 미방문 영역의 운영자료가 올바르게 함께 확정된다.
- 탭·터미널 이동 후 수정 내용이 유지된다.
- 자동 저장·스냅샷·실행 등록 중 실패 시 불완전한 실행을 남기지 않는다.
- 진행 중 요청이 있어도 새 요청은 다른 SMLT_ID로 등록된다.
- 이후 현재상태 수정 및 재실행이 이전 실행의 조건·리소스·결과를 바꾸지 않는다.

### ID·CAST 연계

- 사용자 동시 요청 및 일일 결과 동시 수신에서 ID가 중복되지 않는다.
- 결과가 없는 실행 중 마스터도 MAX 계산에 포함된다.
- 사용자 결과의 마스터·요청·이력·설정·상세 결과가 모두 동일 SMLT_ID를 사용한다.
- 일일 결과는 수신 시 공통 ID를 발급받고 같은 마스터 체계에 들어간다.
- 결과 재수신과 여러 모델·터미널 결과 수신에서 실행이 중복 생성되지 않는다.
- 순환 리소스 번호 재사용이 활성 요청이나 과거 실행의 매칭을 깨뜨리지 않는다.
- 회차 및 추가 실행 차단 로직의 잔여 참조가 없다.

### 조회 및 이관

- 권한 있는 다른 사용자가 실행이력·결과·실행 당시 조건을 조회할 수 있다.
- 현재상태는 공개 조회 경로와 분리된다.
- 최초 저장자, 최대 기존 SMLT_ID 선택 및 부모·자식 묶음 기준이 이관 결과에 반영된다.
- 선택되지 않은 조건, 기존 회차, 미연결 요청·결과도 원본·대응표에서 추적할 수 있다.
- 이관 전후 상세 결과 건수와 주요 지표가 일치한다.
