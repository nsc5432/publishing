# 혼잡등급 대기시간 기준 전환 및 정수형 변경 구현 계획

작성일·정책 확정일: 2026-10-24

상태: 사용자 인터뷰 및 정수형 재검토 완료 / 구현 전

대상: 혼잡등급 기준정보, 등급 판정, 혼잡해소·시설 추천, Java 참조 사본, React·목업·API 문서

작업 범위: 이 문서에 따라 코드를 구현하고 검증한다. 이 문서 갱신 시점에는 코드·DB 변경을 수행하지 않았다.

## 1. 새 세션에서 먼저 읽을 결론

**이 문서의 확정 정책을 기준으로 구현한다. 이전 초안의 권장안이나 현행 인원 기준 동작을 새 정책으로 오인하지 않는다.**

1. 체크인·출국장 모두 DB 기준표를 조회해 **직전 30분 동안 처리된 여객의 평균 대기시간**으로 등급을 판정한다.
2. DB의 MIN/MAX는 **NULL이 없는 정수 분**이다. 조회 DTO까지 `BigDecimal → int`로 변경하고, 도메인에서는 초 단위 정수 경계로 변환한다.
3. 평균 대기시간은 소수 초를 유지한다. 올림·반올림·절삭한 표시값을 등급 판정이나 정렬에 사용하지 않는다.
4. 해소·추천도 같은 지표를 사용한다. **미래의 직전 30분 처리 여객 평균을 예측**해, 목표시간 안에 NORMAL 이하가 되는 최소 시설 수를 찾는다. 같은 예상 유입을 계속 감당할 수 있도록 처리능력도 유입보다 커야 한다.
5. 신규 여객 예상 대기시간이나 정상상태 Erlang C 평균을 등급·해소 목표 대신 사용하지 않는다. 시간 상한을 목표 인원으로 환산하는 이전 초안의 방식도 채택하지 않는다.
6. 미관측·처리 여객 0명·30분 자료 부족은 **산정 불가와 중립색**으로 표시한다. FREE/NORMAL로 대체하지 않는다.
7. 카드와 혼잡 알림은 평균 대기시간이 긴 시설부터 표시한다. PRIME TIME은 기존 대기인원 피크를 유지한다.
8. 과거 결과도 조회 시점의 DB 기준으로 판정한다. 실행 당시 등급표를 보존하는 스냅샷·이력은 이번 범위에 추가하지 않는다.

남은 것은 업무 정책 재인터뷰가 아니라 **원천 자료·시간축 확인, 미래 이동평균 예측 설계, API 계약 구체화와 검증**이다.
이 저장소의 `java/`는 참조 사본이다. 실제 백엔드 컴파일·Oracle·CAST 검증은 별도 환경에서 수행하며, 여기서 완료했다고 주장하지 않는다.

### 1.1 이전 초안에서 대체된 내용

다음 항목은 검토 이력이며 이번 구현안으로 사용하지 않는다.

- 등급은 관측 평균, 해소는 신규 여객 예상시간으로 나누는 안 → **두 계산 모두 처리 여객 평균**으로 통일.
- 고정 30분 구간 평균 → **평가시각 직전 30분 이동평균**.
- 소수 초를 ceil한 뒤 판정하는 안 → **소수 원값을 정수 경계와 직접 비교**.
- 조회 DTO의 BigDecimal 유지·도메인만 정수화하는 A안 → **조회 DTO까지 기본형 int**.
- DB 기준표를 정수 초로 바꾸는 안 → **DB는 정수 분 유지, 로직에서 초로 변환**.
- 신규 여객 예상시간을 `Q*(s)`로 환산하는 이전 제6.2절 → **미래 처리 여객 이동평균 예측**으로 대체.
- 인원 기준 Phase 0를 별도로 먼저 적용하는 제안 → 필수 선행 단계로 두지 않는다. 확정된 단위·경계·입력 의미를 함께 전환한다.

## 2. 사용자 확정 정책

### 2.1 결정표

| 항목 | 확정 내용 |
|---|---|
| 등급표 의미 | FREE·NORMAL·BUSY·VERY_BUSY 모두 개인 대기시간 기준 |
| 시설 범위 | 체크인·출국장 모두 적용. 체크인은 기존 CC 공용 Queue, 출국장은 기존 SC+SR 범위를 유지하고 LGT를 임의 포함하지 않음 |
| DB 단위·값 | 정수 분, MIN/MAX 모두 NULL이 아닌 값이 들어온다는 사용자 보장. DB 제약의 존재를 확인한 것은 아님 |
| 기준 공유 | 체크인·출국장에 같은 경계 적용. 각각 시설그룹 02/04로 조회하는 구조 유지 |
| 등급 지표 | 직전 30분 동안 처리된 여객의 평균 대기시간 |
| 집계 구간 | 평가시각 t에 대해 [t−30분, t). 예: 10:10 → 09:40~10:10 |
| 평균 계산 | 처리 여객수 가중평균. 단순 평균이나 시설별 평균의 최댓값으로 바꾸지 않음 |
| 소수 처리 | 원값 비교. 19분 59.5초는 FREE, 정확히 20분은 NORMAL |
| 해소·추천 지표 | 시설 변경 후 미래의 직전 30분 처리 여객 평균 |
| 해소 목표 | 지정한 시간 안에 평균 대기시간을 NORMAL 이하로 낮춤. 현재 DB 기준으로 40분 미만 |
| 추천 안정 조건 | 같은 예상 유입이 계속될 때 대기열이 다시 늘어나지 않도록 전체 처리능력 > 예상 유입 |
| 미관측·미운영 | 평균을 구할 수 없으면 산정 불가·중립색. 기존 혼잡 enum에 임의 상태 추가 금지 |
| 하루 시작 자료 부족 | 전날 자료가 없어 직전 30분을 채우지 못하면 산정 불가. 당일 일부 구간만으로 평균을 내지 않음 |
| 카드·혼잡 알림 순서 | 평균 대기시간 내림차순 |
| PRIME TIME | 기존 대기인원이 가장 많은 시각 유지 |
| 과거 결과 | 조회 시점 DB 기준으로 재판정. 과거 등급·색상이 달라질 수 있음 |
| 정수화 범위 | 등급표 조회 DTO와 도메인 기준값. 평균·유입률·처리율·FIFO 소수 용량은 대상 아님 |

정렬 동률은 대기인원 내림차순, 이후 시설 식별자 등으로 안정적으로 정렬하는 구현 기본값을 사용한다.
산정 불가 항목은 정상 판정 항목 뒤에 둔다. 대표 등급은 산정 가능한 시설 중 최고 심각도를 사용한다.
일부 시설이 미관측이어도 이를 FREE로 간주하지 않으며, 전부 산정 불가이면 대표값도 산정 불가다.

### 2.2 DB 경계와 로직 해석

두 시설그룹 모두 다음 값을 사용한다. 아래 값은 실DB 조회 결과가 아니라 **사용자가 확정한 입력 전제**다.

| 등급 | DB MIN_VL (분) | DB MAX_VL (분) | 도메인 판정 범위 (초) |
|---|---:|---:|---|
| FREE | 0 | 19 | 0 ≤ W < 1200 |
| NORMAL | 20 | 39 | 1200 ≤ W < 2400 |
| BUSY | 40 | 59 | 2400 ≤ W < 3600 |
| VERY_BUSY | 60 | 9999 | 3600 ≤ W < 600000 |

변환은 한 곳에서 다음과 같이 수행한다.

```java
int minSec = minVl * 60;
int maxExclusiveSec = (maxVl + 1) * 60;
```

- DB의 19는 19분 00초가 아니라 **19분대 전체**를 포함한다. 다음 분 시작을 배타적 상한으로 쓰므로 19:59.5도 누락되지 않는다.
- NORMAL의 목표 경계는 39분 그대로도, 39:59를 포함 상한으로 만든 값도 아니라 **40분 미만**이다.
- 기준은 DB에서 읽어 계산한다. 운영 로직에 20/40/60을 다시 하드코딩하지 않는다. 위 숫자는 설명·검증 fixture다.
- VERY_BUSY의 9999는 실제 최종 분 상한이다. NULL이나 무한대 표기로 임의 재해석하지 않는다. 600000초 이상은 기준 범위 밖 오류/산정 불가로 구분하고, FREE로 돌리지 않는다.
- 최대 변환값 600000은 int 범위 내다. 음수·구간 역전·중복·누락·공백·잘못된 코드 검증은 유지한다.

## 3. 현행 코드 조사 결과와 전환 지점

아래 내용은 변경 전 동작이다. 줄 번호는 조사 시점 참고이며 구현 시 심볼로 위치를 찾는다.

```text
TN_PM_PSG_PRCS_GRD.MIN_VL / MAX_VL
  → CastDsbdMapper.retrievePsgPrcsGradeList
  → PsgPrcsGradeRawDto(BigDecimal)
  → CastCgnGradeServiceImpl → CgnGradeScale
      ├─ statusOf(현재 대기인원)
      │    ├─ 대시보드 카드·시설 칩
      │    └─ ChknQueueDay → 체크인 맵·상세·알림
      └─ getNormalMax → toTargetQueueCnt(현재 intValue)
           → FcltQueueClearance → 해소시간·총 소요 시설 수

별도 인원 기준 경로:
CongestionStatus.ofWtngPsgCnt(80 / 220 / 420명)
  → 터미널 요약·출국장 맵·출국장 상세·알림
```

- `normalMax` 소비처는 조사 시점에 3곳이다: `CastDsbdServiceImpl:251`, `CastFcltQueueScenarioServiceImpl:116`, `ChknQueueDay:119`.
  모두 `FcltQueueClearance.toTargetQueueCnt(BigDecimal)`을 거친다. 타입만 int로 바꾸면 시간 숫자를 명으로 읽는 오류가 컴파일을 통과한다. 이 변환 메서드부터 제거·명시적 교체해 옛 호출을 드러낸다.
- `CgnGradeScale.statusOf(int waitingCount, String)`도 단순히 인자 이름만 바꾸면 부족하다.
  평균은 소수이며 미산정일 수 있다. 새 입력 계약과 호출 경로를 함께 바꾸고 인원 전달이 남지 않았는지 확인한다.
- `CongestionStatus.java:14–16`의 80/220/420명 상수와 `ofWtngPsgCnt` 사용 경로는 전부 DB 시간 기준으로 전환한다.
  enum 문자열과 `ofGradeCode` 매핑은 유지한다.
- `CastCgnGradeServiceImpl`은 CHKN `02`, DEP `04`를 조회한다. 값이 같아도 서로 다른 그룹을 계속 조회한다.
  현재 SQL은 터미널별 기준 키를 갖지 않으며, 이번 범위에서 임의로 키를 늘리지 않는다.
- `java/utils/SmltUtils.java`의 별도 `PsgPrcsGrd` 판정기는 저장소 내 호출이 발견되지 않았다.
  미사용 여부를 재확인하고 제외 사유를 남긴다. 기존 코드·주석을 임의 삭제하지 않는다.

## 4. BigDecimal → int 확정 설계

### 4.1 변경 범위

| 대상 | 변경·유지 |
|---|---|
| `PsgPrcsGradeRawDto.minVl / maxVl` | BigDecimal → 기본형 int. 이름 유지, 단위는 DB와 같은 분 |
| `CgnGradeScale` 내부 구간 | int 초. 하한 포함·상한 배타적 |
| NORMAL 기준 getter | 내부 이름은 `getNormalUpperExclusiveSec`처럼 단위·배타성을 드러내도록 변경 |
| 등급 판정용 평균 | 소수 초 유지. nullable Double 또는 기존 계산 상태 구조로 산정 불가 구분 |
| 평균·λ·μ·ρ·이론 계산 | 기존 소수형 유지 |
| FIFO 서비스율·소수 처리용량 | 기존 BigDecimal 등 유지 |
| 다른 API의 BigDecimal 수량·목표시간 | 이번 등급표 정수화를 이유로 바꾸지 않음 |

DB 값이 정수이고 NULL이 없다는 전제에서 조회 DTO에 Integer나 BigDecimal을 남겨야 할 요구는 없다.
DB NUMBER 컬럼의 물리 타입을 변경하는 작업도 필요하지 않다.
사용자가 확정한 전제와 달리 NULL·소수가 실제로 발견되면 데이터를 수정하거나 전제 불일치를 보고한다.
묵시적 절삭을 정상 정책으로 정하지 않는다.

### 4.2 기준정보 검증과 관측값 검증 분리

- 기준표의 4개 등급 존재, 그룹 일치, 코드 중복, 음수, 역전, 경계 공백·겹침을 검사한다.
- 변환 후 연속성은 `previous.maxExclusiveSec == current.minSec`이다. 이전 초안의 정수 초 양끝 포함 `max+1` 검사를 섞지 않는다.
- 기준정보 누락·오류는 설정 오류로 처리한다. 고정 인원 상수나 임의 시간 기준으로 fallback하지 않는다.
- 평균의 NULL·NaN·무한대·음수, 처리인원 0, 불완전 관측 구간은 관측/예측 산정 불가로 분리한다.
- **DB 기준표의 NOT NULL 보장과 관측 평균의 nullable 여부는 별개다.**

## 5. 공용 30분 이동평균

### 5.1 관측 평균과 시각 의미

평가시각 `t`의 등급·정렬용 평균은 다음과 같다.

```text
W(t) = [t−1800초, t)에 처리된 여객의 대기시간 합(초)
       / 같은 구간에서 처리된 여객수
```

- 관측 구간 전체가 확보되고 분모가 양수일 때만 산정한다. 관측된 0초는 유효한 값이다.
- 처리인원 0명은 평균 0초가 아니다. Queue가 남아 있거나 운영 시설이 0개인 경우도 미관측을 FREE로 만들지 않는다.
- 단순 평균, 최대 평균, 현재 Queue/처리능력, 표시용 분을 위 지표로 대신하지 않는다.
- 같은 `smltId / tmnlId / 평가시각 / 시설`에서 카드·칩·맵·상세·알림의 등급과 원값이 일치해야 한다.
- 화면이 선택한 10:10의 평균은 09:40~10:10이다. 기존의 10:10~10:40 고정 구간을 이름만 이동평균으로 바꾸지 않는다.
- 현재 카드·팝업은 `hhmm`를 슬롯 시작으로 읽고 `baseDt`에 30분 뒤 슬롯 끝을 내려주는 경로가 있다.
  새 평가시각과 원천 구간을 함께 정렬하고 `baseDt`를 실제 계산 기준시각으로 유지한다.
  화면의 임의 +30분 보정으로 서로 다른 시각을 맞추지 않는다.
- 전날 자료 없이 당일 00:00부터 시작하면 00:00~00:30 전에는 산정 불가다.
  정확히 00:30부터도 [00:00,00:30) 전체 자료와 처리 여객이 있어야 산정한다.
- 당일 일부 구간의 평균이나 전날 마지막 값을 채워 넣지 않는다. 구간 중간 결측도 자료 부족으로 구분한다.
- 하루치 조회·30분 슬롯 응답·타임라인의 클라이언트 이동 방식은 유지한다.
  이동평균은 서버에서 각 평가시각의 직전 구간으로 생성한다. 눈금 이동마다 API를 부르지 않는다.
  원천 해상도와 다른 시각을 지원할 때는 집계·예측 모델의 해상도와 한계를 명시한다.

### 5.2 현재 원천의 제약과 선행 구현 과제

다음은 코드 재확인 결과다. 이미 미래 평균 계산이 완성되어 있다고 가정하지 않는다.

`Hr`라는 필드명만 보고 단위를 추정하지 않는다.

## 6. 같은 평균을 사용하는 미래 해소·추천

### 6.1 평가 모델

시설 수량 `s`를 평가시각 `t`부터 적용하고, 현재 적체·기존 대기 연령·예상 유입·처리능력을 반영해 미래 처리 이력을 예측한다.
미래시각 `u`에서도 관측과 동일하게 **[u−30분,u)에 처리된 여객의 대기시간 합 / 처리 여객수**를 계산한다.

- 창 안의 `t` 이전 부분은 실제 처리 이력, `t` 이후 부분은 시나리오 예측 이력이다.
- 기존 대기자의 대기시간은 `t`에서 0으로 초기화하지 않는다.
- 이미 처리된 여객의 과거 대기시간 합은 시설을 늘려도 바뀌지 않는다. 기존 관측 평균이 즉시 감소한다고 계산하지 않는다.
- 관측값과 예측값은 같은 지표지만 근거가 다르므로 화면에 현재 관측 평균·시나리오 예측 평균을 구분한다.
- COUNT·TIME·보유 수량 시나리오·추천 재검증은 모두 하나의 평가기를 사용한다.
- 신규 여객 `(Q+1)/C` 예상시간, Erlang C 평균, Little's Law, 기존 Q* fluid 해소시간을 이 평균의 대체값으로 쓰지 않는다.
- 기존 진단 지표를 계속 제공할 경우 기존 이름·의미를 유지하고 목표 판정과 분리한다.

### 6.2 원천 확보와 예측 상태

미래에 처리될 여객의 평균은 `Q0 / λ / μ / 현재 평균`만으로는 유일하게 정해지지 않는다.
최소한 다음 자료 또는 이를 재구성할 근거 있는 모델이 필요하다.

1. 평가시각 이전 30분의 처리인원·대기시간 합 이력과 구간 유효성.
2. 평가시각 현재 Queue의 도착시각별 잔여 인원 또는 대기 연령을 나타내는 상태.
3. 미래 유입과 시설당 처리율 추정 및 단위·해상도.
4. CAST 결과 timestamp가 구간 시작인지 끝인지, 10분 원천을 분별 예측에 사용하는 경우의 재구성 근거.
5. 당일 자정 초기 Queue가 있을 때 도착 연령과 관측 범위를 어떻게 확보하는지.

체크인은 기존 FIFO 상태를 활용·확장하는 방향을 우선 검토한다.
출국장의 현재 10분 집계만으로 정확한 잔여 대기 연령이나 임의분 원천을 복원할 수 있다고 가정하지 않는다.
필요 자료를 확보할 수 없으면 그 예측은 산정 불가로 처리하고 구체적인 부족 자료를 보고한다.
근거 없는 정적 공식으로 바꿔 같은 지표를 구현했다고 표시하지 않는다.
근사 모델을 사용하게 되면 가정·정밀도·사유를 API 근거와 검증에 드러낸다.

이 항목은 **정책 미확정이 아니라 구현 전 확인할 데이터·모델 의존성**이다.
자료 부족을 이유로 신규 여객 지표로 몰래 바꾸거나 정상 수치를 만들어 내지 않는다.

### 6.3 해소 목표·안정 조건·추천 탐색

`B`를 DB NORMAL의 배타적 상한 초, `H`를 요청한 목표 해소시간, `λ`를 예상 유입(명/시간), `μ`를 시설당 처리율(명/시간/개)로 둔다.

- 목표 판정은 `W(u) < B`다. 현재 기준 B=2400초이며 정확히 2400초는 BUSY다.
- `clearOf(s)`는 미래 이동평균을 평가해 목표 도달시각을 찾는다. 이미 유효한 관측 평균이 목표 미만이면 도달시간은 0이다.
- 추천 후보는 H 안에 목표에 도달해야 한다. 목표시각의 예측 평균도 재평가해 충족 여부를 확인한다.
- 모든 추천 후보는 `C(s)=s×μ > λ`도 충족해야 한다. λ=0에서도 C(s)>0이어야 한다.
  μ>0·λ≥0이면 안정 하한은 `floor(λ/μ)+1`이다. 현행 λ=0일 때 0개를 반환하는 예외를 그대로 재사용하지 않는다.
- 이미 목표 미만이어도 불안정한 수량을 추천하지 않는다. 도달시간 0과 추천 수량의 적절성은 별도 평가다.
- λ=0·빈 Queue·시설 0개 등은 실제 미래 처리 여객 존재 여부와 평균 유효성을 함께 평가한다.
  처리 여객이 없는 미래 창을 0초로 간주해 0개를 목표 충족으로 추천하지 않는다.
- 후보 수량마다 동일 상태에서 시뮬레이션한다. 후보 간 상태 누적이나 현재 수량 결과의 단순 비례 환산을 금지한다.
- 평균은 처리되는 여객 구성이 바뀌므로 후보 수량에 대해 단조라고 단정하지 않는다.
  이분 탐색·폐쇄형 공식을 쓰려면 단조성 근거가 필요하다. 최소 충족 수량을 실제 재평가해 보장한다.
- 계산 해상도·예측 탐색 범위·수량 탐색 상한·int 표현 범위·종료 조건을 명시한다.
  탐색 범위 부족을 수학적 도달 불가능으로 오인하지 않는다.
- 추천 수량을 평가기에 다시 넣어 목표시간·안정 조건을 검증한 후 `goalMet`를 설정한다.
- 보유 수량을 넘는 총 소요 수량 추천과 실제 보유 수량만 쓴 `totScenario`는 구분한다.
  기존 카드 `reqCnt`는 추가 수량이 아닌 총 소요 수량이며 이름·의미를 유지한다.
- 미산정과 도달 불가, 이미 목표 충족(0)을 구분한다. 기존 `Computed`·계산 상태 체계를 우선 활용하고 실패 사유를 제공한다.

### 6.4 개인 대기시간과 해소시간 구분

- 개인 평균 대기시간 목표: DB NORMAL 상한으로부터 계산한 **40분 미만**.
- `targetMinutes / recommend.targetMin / dfltTargetMin`: 그 목표를 달성하는 데 허용하는 시간. 기본 **30분** 유지.
- 예: “30분 안에 직전 30분 처리 여객 평균 대기시간을 40분 미만으로 낮춘다.”
- 카드 `reqCnt`·혼잡해소 예상시각은 TIME 기본 30분 팝업과 같은 기준시각·입력·평가기 결과여야 한다.

### 7.2 API 계약을 구현 전에 함께 정리할 것

이 절은 확정 정책을 구현하는 계약 방향이다. 실제 추가 필드명과 타입은 Java·React·API 문서를 동시에 맞춘다.
기존 DTO 필드명을 임의 리네임하거나 단위를 바꾸지 않는다.

- `FcltQueueScenarioDto.targetQueueCnt`는 **명 단위 계약**이다. 여기에 39·2400 등 시간 숫자를 넣지 않는다.
  새 평균 목표에는 단일 환산 인원이 없으므로 이 방식에서는 미적용을 null로 표현하는 방향으로 정리한다.
  현재 Java는 Integer, React는 number이므로 React도 `number | null`로 맞추고 목표 설명에서 사용하지 않는다.
- 시간 목표는 `normalUpperExclusiveSec` 같은 별도 필드로 전달하고 “미만” 경계를 명시한다.
  이동평균 관측 구간·처리수·평균·유효성 및 시나리오 예측 평균·산정 근거도 필요한 수준으로 추가한다.
- 기존 `nextWtngSec / nextWtngMetric`은 신규 여객 진단이다. 이 이름으로 처리 여객 이동평균을 내려보내지 않는다.
  목표용 미래 평균은 별도 필드와 근거로 제공한다.
- `QueueMetricDto`의 상태·방식·사유 구조를 우선 재사용한다. 기존 방식 코드의 의미를 바꿔 새 알고리즘을 숨기지 않는다.
- `cgnStatus`는 산정 불가를 전달할 수 있도록 관련 DTO·타입에서 nullable을 명시하고 별도 계산 상태·사유와 함께 처리한다.
  기존 혼잡 enum 문자열에 UNKNOWN 같은 값을 임의 추가하지 않는다.
- `reqCnt` 등 기존 nullable 수량 필드는 산정 불가일 때 null을 유지한다.
  DB 기준값이 NOT NULL이라는 이유로 결과 필드까지 기본형/0으로 바꾸지 않는다.
- API 필드명·enum·DOM id·기존 className·CSS 변수·색상 결합 값은 보존한다.
  nullable 확장과 새 필드 추가는 서버·화면·목업·문서에 함께 반영한다.

### 7.3 미관측 렌더링과 목록의 정확한 의미

현재 일부 `view.ts`는 누락된 `cgnStatus`를 NORMAL로, 대시보드 EMPTY는 FREE로 채운다.
이 fallback과 상태별 테마 직접 조회를 전부 점검해 산정 불가 분기를 추가한다.

- 확인 위치: `terminalMap/view.ts`, `departureHall/view.ts`, `checkinCounter/view.ts`,
  `dashboard/view.ts`, `dashboard/components/TerminalSummary.tsx` 및 카드·칩.
- `CongestionLevel`·`NoticeLevel` 같은 기존 CSS 결합 enum을 임의 확장하지 않는다.
  가용성 필드·별도 렌더 분기·추가 data 속성/중립 스타일을 사용하고, 기존 `.chip.gray` 등은 재사용 가능하다.
- “이미 목표 인원 이하”, “대기인원 N명 이하 기준” 문구를 새 평균 목표와 경계로 바꾼다.
  표기 가공은 페이지 `view.ts`에 모은다.

정렬 대상은 다음과 같다.

1. **대시보드 T1/T2 하단 ‘체크인카운터’·‘출국장’ 카드 안의 시설 순서.**
   처음 표시할 아일랜드/출국장과 좌우 화살표 순서를 평균 대기시간 내림차순으로 바꾼다.
   카드 두 장의 배치 순서를 바꾸는 뜻이 아니다. 현재 `FcltCard.tsx`는 서버 배열 첫 항목을 기본 선택한다.
2. **맵형태보기·출국장 화면 상단의 혼잡 시설 알림 목록.**
   먼저 표시할 시설을 같은 평균 기준으로 정렬한다. 기존 BUSY/VERY_BUSY 알림 대상·최대 6건 규칙은 유지한다.
   산정 불가를 혼잡 조치 대상이나 정상 상태로 임의 분류하지 않는다.

PRIME TIME은 인원 최대 시각을 계속 사용한다.
시간 기준 대표 혼잡등급을 인원 피크의 한 시설에서 다시 인원으로 판정하지 않도록 분리한다.

## 8. DB·전환·문서 적용

### 8.1 DB 확인과 적용

사용자가 기준표의 단위·정수값·NOT NULL 전제를 확정했으므로 이를 미결정 정책으로 다시 취급하지 않는다.
아래는 배포·매핑 검증이다.

1. `PMOWN.TN_PM_PSG_PRCS_GRD`의 실제 컬럼·등급코드·시설그룹 02/04를 확인한다.
   저장소에는 이 테이블의 DDL·시드가 없다. `cast-ddl.sql`의 다른 테이블 MIN_VL 정의를 근거로 삼지 않는다.
2. 두 그룹의 기존 행을 백업하고 사용자 확정 분 경계를 입력하는 적용 SQL·검증 SQL을 준비한다.
   NULL 및 `MIN_VL != TRUNC(MIN_VL)`·`MAX_VL != TRUNC(MAX_VL)` 등으로 사용자 전제와 실제 값의 불일치를 확인한다.
   Java int 전환을 위해 DB NUMBER 타입을 변경하지 않는다.
3. 같은 기준표를 읽는 저장소 밖 프로그램이 있는지 확인한다.
   새 분 단위 데이터와 옛 인원 기준 코드가 섞이지 않도록 코드·기준표 전환 순서를 맞춘다.
4. 새 정책에서는 과거 결과도 현재 기준으로 판정한다. 과거 기준 스냅샷·별도 기준 이력은 만들지 않는다.
5. 배포 실패 시 이전 코드와 이전 기준표를 함께 복원할 수 있도록 백업·복구 절차를 준비한다.

## 10. 검증 계획

### 10.1 경계·타입·유효성

- DTO minVl/maxVl이 기본형 int 분이며 도메인만 초로 정규화되는지 확인.
- FREE/NORMAL/BUSY/VERY_BUSY 각 경계 직전·동일·직후, 소수 초 확인:
  1199.5 → FREE, 1200 → NORMAL, 2399.5 → NORMAL, 2400 → BUSY, 3599.5 → BUSY, 3600 → VERY_BUSY.
- 599999.5초는 VERY_BUSY, 600000초는 기준 범위 밖으로 처리.
- 구간 누락·중복·역전·공백·겹침·미지원 등급코드·다른 시설그룹 행 거절.
- DB NULL·소수가 발견되면 사용자 전제 불일치를 보고. int 매핑의 묵시적 절삭을 검증 통과로 취급하지 않음.
- 같은 인원인데 시간이 다르면 등급이 다르고, 인원이 달라도 같은 평균이면 같은 등급인지 확인.

### 10.2 이동평균·시각·미관측

- 평가시각 10:10에 09:40~10:10 사용, 이후·이전 구간이 섞이지 않음.
- 처리수 가중평균 확인. 예: 1명×10분 + 9명×30분이면 평균 28분.
- 분·10분 원천과 반올림 전 소수값, 서로 다른 화면의 coverage·가중치 일치.
- 자정 직후·00:29는 자료 부족, 00:30은 전체 관측 여부에 따라 산정.
- 시작/끝 행 누락·구간 중간 결측·처리인원 0·평균 NULL·시설 미운영·결과 미수신 구분.
- 실제 처리 여객 평균 0초는 FREE, 처리 여객 0명은 산정 불가.
- 새 기준시각과 baseDt에 이중 +30분 보정이 없음.
- 산정 불가가 NORMAL/FREE fallback이나 기존 테마 인덱싱으로 잘못 표시되지 않음.

### 10.3 미래 평균·해소·추천

- 이전 30분 실제 처리 이력과 이후 예측 이력이 같은 창에서 자연스럽게 교체됨.
- 과거 처리 이력이 시설 변경으로 바뀌지 않고, 기존 대기자의 대기 연령을 초기화하지 않음.
- 현재 평균은 동일하지만 잔여 대기 연령이 다른 Queue에서 미래 결과가 달라지는 사례.
- 이미 목표 미만·목표 동일·목표 초과, H 시점 충족/실패, λ=0, μ 미상, 시설 0개, C≤λ.
- 목표 평균을 단기 충족해도 C≤λ이면 추천 후보 제외. λ=0에서도 C>0 조건 확인.
- 추천 수량을 다시 넣었을 때 H 조건과 C>λ 충족, 더 작은 허용 후보는 불충족인지 검증.
- 이동평균의 후보별 비단조 가능성, 탐색 종료·범위·해상도·정수 수량 한계.
- 미래 창의 처리 여객 0명을 0초 목표 충족으로 오인하지 않음.
- 원천 자료 부족과 도달 불가, 탐색 범위 부족과 수학적 불가능, 목표 도달시간 0 구분.
- 카드와 TIME 기본 30분 팝업의 reqCnt·기준시각·해소시각 일치.
- COUNT/TIME/보유 수량/추천이 동일 평가기 사용. 보유 초과 추천과 totScenario 차이를 표시.

### 10.4 화면·회귀·실환경

- 평균이 45분인 300명 시설보다 평균 65분인 100명 시설이 카드·알림에서 먼저 표시됨.
- 최고 심각도 대표 등급, 산정 불가 중립 표시, 정렬 동률·전부 산정 불가 확인.
- PRIME TIME은 인원 최대 시각 유지. 인원 차트·지표의 단위를 시간으로 바꾸지 않음.
- T1/T2·CHKN/DEP·일일/사용자 결과·과거 결과 조회 확인.
- 타임라인 하루치 조회와 재생·팝업의 조회 방식, 저장·실행 ID 계약 회귀 확인.
- 전환 후 `statusOf(`·`ofWtngPsgCnt(`·`getNormalMax`·`toTargetQueueCnt` 호출을 검색해 인원 판정 잔존 검사.
- 구현 후 `react/`에서 `npx tsc -b`, `npx eslint .` 및 필요한 화면 확인.
  이 저장소에는 일반 테스트 러너가 없으므로 새 검증 방식은 계산 의미·경계·회귀를 확인하는 데 필요한 범위로 정한다.
- Java는 실제 백엔드 레포에서 컴파일·검증하고 Oracle 매핑·실제 CAST 결과와 대조한다.
  이 저장소의 참조 사본만 보고 실환경 성공을 주장하지 않는다.

완료 기준은 **int 기준표 + 원값 기반 직전 30분 평균 + 같은 평균의 미래 예측·안정 추천 + 전 화면/목업/API 일치 + 기준표 동시 전환**이다.
타입만 int로 바꾸거나 신규 여객 예상시간으로 목표를 대체한 상태는 완료가 아니다.
