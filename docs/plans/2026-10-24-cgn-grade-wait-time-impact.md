# 혼잡등급 대기시간 기준 전환 영향도 및 정수형 변경 계획

작성일: 2026-10-24  
상태: 저장소 조사 완료 / 구현 전 정책·실DB 확인 필요  
대상: `CgnGradeScale.normalMax`, 혼잡등급 판정, 혼잡해소·시설 추천, 연관 화면·목업

## 1. 결론

`normalMax`를 대기인원 상한에서 **개인 대기시간 상한**으로 바꾸려면 필드 타입이나 이름만 바꿔서는 안 된다. 현재 코드는 같은 기준표를 다음 두 목적으로 사용한다.

1. 대기인원으로 `FREE / NORMAL / BUSY / VERY_BUSY` 등급을 판정한다.
2. NORMAL 상한을 목표 대기인원 `Q*`로 사용해 해소시간·총 소요 시설 수를 계산한다.

따라서 **등급 판정 입력, 해소·추천 산식, API의 기준 표시, 목업을 함께 변경**해야 한다. 출국장 맵·상세는 별도의 인원 상수로 등급을 판정하므로 공용 클래스 수정만으로 전환되지 않는다.

`BigDecimal → int`는 **기준값을 정수 초로 정규화한다는 조건에서 가능**하다. 다만 실DB 등급표의 단위·소수값·NULL·최댓값을 확인하지 못했으므로, DB 조회 DTO까지 즉시 기본형 `int`로 바꾸는 것은 권하지 않는다. 권장안은 **조회 경계에서 NULL과 변환을 검증하고, 검증된 도메인 기준값은 `int`로 보관**하는 것이다. 처리율·평균·이론 계산까지 일괄 정수화하는 작업은 포함하지 않는다.

이 문서는 코드 수정 계획이다. 실제 Java·React·SQL 변경 및 DB 적용은 수행하지 않았다. Java는 참조 사본이므로 실제 백엔드 빌드·Oracle·CAST 검증은 별도 환경에서 수행해야 한다.

### 1.1 검토 보완 사항 (2026-10-24 재검토)

코드를 다시 대조해 확인·보완한 내용이다.

- **`normalMax` 소비처는 정확히 3곳**이다: `CastDsbdServiceImpl:251`, `CastFcltQueueScenarioServiceImpl:116`,
  `ChknQueueDay:119`. 모두 `FcltQueueClearance.toTargetQueueCnt(BigDecimal)`을 거치므로 이 한 메서드가 시간→인원
  오인의 단일 차단점이다. 타입만 `int`로 바꾸면 시그니처가 `toTargetQueueCnt(int)`로 바뀌어 **컴파일은 통과하고
  의미만 틀어지는** 가장 위험한 상태가 된다. 구현 시 이 메서드를 먼저 제거하거나 이름을 바꿔 호출부 3곳이
  컴파일 오류로 드러나게 한다.
- `CgnGradeScale.statusOf(int, String)`은 이미 `int`를 받는다. 정수 초 판정 입력과 시그니처 모양이 같으므로,
  인자 이름·오류 메시지(`waitingCount`)를 바꾸지 않으면 **호출부가 여전히 인원을 넘겨도 컴파일된다.** 인자를
  `waitSec`로 바꾸고, 인원 호출 경로가 남지 않았는지 grep으로 확인한다(§9).
- `BigDecimal → int`는 **동작을 바꾸지 않는 선행 리팩토링(Phase 0)** 으로 분리할 수 있다. 단위가 아직 인원인 채로
  `CgnGradeScale` 내부 구간만 `int`로 정규화하면(`intValueExact`, 공백 검사 추가) 정책 확정과 무관하게 먼저
  머지·검증할 수 있고, 이후 정책 전환(Phase 1~)과 변경 원인이 섞이지 않는다. 단, 이 경우 DB의 소수 인원값이
  있으면 `intValueExact`가 실패하므로 §7 점검이 선행 조건이다.
- 현행 검증은 **구간 사이 공백을 검사하지 않고**, NORMAL 외 등급(FREE·BUSY·VERY_BUSY)의 존재도 강제하지 않는다.
  정수 구간으로 바꾸면 `prev.max + 1 == cur.min` 연속성과 4개 등급 존재 검사를 함께 넣는 것이 안전하다
  (공백에 값이 떨어지면 `statusOf`가 예외로 화면 조회 전체를 실패시킨다).
- **기준표에 단위 정보가 없다**(`TN_PM_PSG_PRCS_GRD`는 시설그룹·등급·MIN/MAX만 조회). 단위(초/분)를 코드 상수로만
  가정하면 DB 값이 분으로 입력된 순간 조용히 틀린다. 가능하면 기준표 자체에 단위 컬럼을 두거나, 최소한 전환
  시점 값을 §7의 사전 점검으로 확정하고 `CgnGradeScale` 생성자에서 상한 범위(예: NORMAL 상한 ≤ 3600초)를
  sanity 검증으로 둔다.

## 2. 먼저 확정할 정책

사용자 요청으로 확정된 사항은 **NORMAL 상한의 의미가 대기열에서 대기시간으로 변경된다**는 점이다. 아래 항목은 저장소만으로 확정할 수 없다.

| 항목 | 제안 및 확인 사항 |
|---|---|
| 기준표 전체의 의미 | `normalMax`만 시간을 넣고 다른 구간을 인원으로 남길 수 없다. 같은 `MIN_VL / MAX_VL`을 쓰는 FREE·NORMAL·BUSY·VERY_BUSY 전체가 시간 구간인지 확인한다. 이하 계획은 전체가 시간 기준으로 전환되는 것을 전제로 한다. |
| 시간 단위 | 도메인은 정수 초를 권장한다. DB의 초/분 단위와 시설그룹별 실제 기준값은 담당자·실데이터로 확정한다. |
| 등급에 사용할 시간 | **구간 처리 여객의 평균 대기시간**, **현재 줄 끝 신규 여객의 예상 대기시간**, **Erlang C 정상상태 평균 대기시간**은 서로 다르다. 어느 지표가 업무 기준인지 확정한다. |
| 관측 구간·집계 | 동일 시설·시각에서 카드·맵·상세가 같은 구간과 집계를 사용하도록 정한다. 현재 CHKN과 DEP의 집계 방식이 다르다(§4). |
| 소수 초 | 기준을 정수 초로 관리하더라도 관측 평균·모델 결과는 소수다. 판정 시 올림할지, 원값으로 비교할지 정한다. 표시용 분 반올림 값을 판정에 재사용하지 않는다. |
| 미관측·미운영 | 처리인원 0, 평균시간 NULL, 시설 0개, 대기인원만 존재하는 경우를 정상 대기시간 0초와 구분한다. 기존 enum에 임의 상태를 추가하지 않는다. |
| 순위·피크 | 등급 전환이 카드 정렬·상위 알림·PRIME TIME 선정도 시간순으로 바꾸는 요구인지 확인한다. 인원순 유지도 가능한 별도 정책이다. |

**권장 기본안:** 등급표의 시간 단위를 정수 초로 통일하고, 등급 판정 지표를 하나 정한 뒤 모든 관련 화면에 공유한다. 해소·추천이 사용하는 미래 시간 지표도 명시한다. 관측 평균을 등급에 쓰면서 해소에는 신규 여객 예상시간을 쓰기로 한다면, 두 지표가 다름을 화면과 문서에 드러내야 한다. 이 선택을 이름 변경으로 감추지 않는다.

## 3. 확인된 의존 관계

```text
TN_PM_PSG_PRCS_GRD.MIN_VL / MAX_VL
  → CastDsbdMapper.retrievePsgPrcsGradeList
  → PsgPrcsGradeRawDto(BigDecimal)
  → CastCgnGradeServiceImpl → CgnGradeScale
      ├─ statusOf(현재는 대기인원)
      │    ├─ 대시보드 카드·시설 칩
      │    └─ ChknQueueDay → 체크인 맵·상세·알림
      └─ getNormalMax → toTargetQueueCnt(현재는 단순 intValue)
           → FcltQueueClearance → 해소시간·총 소요 시설 수
                ├─ 대시보드 카드
                ├─ 혼잡해소 시나리오 팝업 COUNT / TIME
                └─ ChknQueueDay.recommendOf → 맵·상세 추천

별도 경로: CongestionStatus.ofWtngPsgCnt(80 / 220 / 420명)
  → 터미널 요약 등급·출국장 맵·출국장 상세·알림
```

현재 `CastCgnGradeServiceImpl`은 CHKN 그룹 `02`, DEP 그룹 `04`를 선택한다. SQL은 시설그룹으로만 조회하며 터미널·지표·단위 컬럼은 조회하지 않는다. 새 정책이 터미널별 기준을 요구할 경우에는 별도의 조회 키·스키마 검토가 필요하며, 이번 변경만으로 그런 구분이 있다고 가정하지 않는다.

## 5. BigDecimal → int 가능 여부와 권장 범위

### 5.1 타입별 판단

| 대상 | 판단 | 이유·조건 |
|---|---|---|
| `CgnGradeScale.normalMax` | **조건부 가능, 권장** | 정수 초·음수 금지·int 범위를 보장한 뒤 `int`로 저장한다. |
| 등급표 도메인 `min / max` | **함께 전환 권장** | NORMAL 상한만 int로 바꾸면 나머지 구간에 BigDecimal 비교가 남는다. 같은 단위·타입으로 정규화한다. |
| `PsgPrcsGradeRawDto.minVl / maxVl` | **조회 경계 전략 선택 필요** | NULL 검출을 보장하려면 `Integer`가 적절하다. 기본형 int의 기본값 0으로 결측을 숨기지 않는다. |
| 평균·유입률 λ·시설당 처리율 μ·부하율 ρ | **일괄 전환 제외** | 소수가 의미 있으며 정수 나눗셈은 등급 경계·추천·해소시간을 왜곡한다. |
| FIFO의 BigDecimal 서비스율·소수 처리용량 | **전환 제외** | `ChknQueueSeries.serviceRateOf` 등은 등급 기준표와 별개 계산이다. |
| 다른 API 요청의 BigDecimal 수량·목표시간 | **별도 검토 사항** | 현재 소수 요청을 검증·거절하는 계약이다. 기준표 정수화만을 이유로 함께 바꾸지 않는다. |

### 5.2 두 가지 구현안

**A. 도메인 정수화 우선 — 안전한 기본안**

- 조회 DTO는 BigDecimal로 두고, 도메인 생성 시 단위를 초로 정규화한 다음 `intValueExact()`로 변환한다.
- NULL·음수·소수 초·범위 초과를 구체적인 기준정보 오류로 처리한다. 분 단위 소수 `0.5`는 30초로 정확 변환 가능하지만, 초 미만 값은 별도 정책 없이는 거절한다.
- `CgnGradeScale` 내부 구간과 상한·getter는 모두 int가 되므로 비교 로직에서 BigDecimal이 사라진다.
- DB의 소수값을 JDBC 정수 매핑이 조용히 절삭하는 문제를 피할 수 있다.

**B. 조회 DTO까지 정수화 — 사전 점검 후 가능**

- DB 기준표를 정수 초로 관리하고 정수·범위·NULL 제약 또는 동등한 검증을 보장한다.
- `PsgPrcsGradeRawDto.minVl / maxVl`을 `Integer`로 바꿔 조회한 뒤, 도메인에서 검증하고 int로 복사한다.
- JDBC/MyBatis가 잘못된 소수값을 자동 절삭하지 않도록 DB 제약 또는 정확 변환 TypeHandler를 준비한다. 타입만 Integer로 바꾸는 것으로 검증을 대신하지 않는다.

요구가 “도메인에서 BigDecimal을 없애기”라면 A로 충족한다. “조회 DTO에서도 BigDecimal을 없애기”까지라면 B를 선택한다. **어느 경우에도 기존 `intValue()`의 묵시적 절삭을 전환 정책으로 사용하지 않는다.**

### 5.3 정수 시간 경계

- 현재 양끝 포함 `[min,max]` 구간을 유지하고 판정 입력도 정수 초로 정규화한다면, 다음 구간의 시작은 이전 `max+1`이어야 한다. 예: `[0,300]`, `[301,600]`. 기존 분 경계에 각각 60을 곱하면 초 단위 공백이 생길 수 있으므로 구간을 다시 정의한다.
- 소수 관측초를 정수 입력으로 바꾸는 권장 정책은 올림이다. 예를 들어 600.1초를 600초로 절삭해 NORMAL에 넣지 않는다. 다만 기존 CHKN 평균은 이미 초 반올림된 값이므로 정밀 원값을 사용할지까지 결정한다.
- 소수 입력을 그대로 비교하려면 연속시간 경계 정책을 따로 정의한다. 정수 구간의 연속성과 소수 구간의 연속성을 혼용하지 않는다.
- `max+1`, 분→초 환산은 long 또는 정확 연산으로 계산한 뒤 범위를 검사한다. 마지막 등급의 상한 표현과 상한 초과 처리도 정한다. NULL을 무한 상한으로 해석하는 현행 계약은 없다.

## 6. 시간 목표에 맞는 해소·추천 설계

### 6.1 단순 치환이 불가능한 이유

현재 산식은 명/시간 처리율 기준 `t초=(Q0−Q*)/(sμ−λ)×3600`이며 `Q*`의 단위는 명이다. 시간 상한 `W*`를 이 자리에 직접 넣으면 차원이 맞지 않는다. 또한 같은 시간 상한에 해당하는 허용 인원은 운영 시설 수와 처리속도에 따라 달라진다.

다음 세 시간 지표를 구분한다.

| 지표 | 현재 제공 경로 | 전환 시 주의점 |
|---|---|---|
| 관측 평균 대기시간 | `avgWaitSec / avgWtngSec` | 이미 처리된 여객의 과거 구간 평균이다. 시설을 늘렸다고 같은 관측값이 즉시 줄어들지 않는다. 미래 해소를 예측할 별도 모델이 필요하다. |
| 신규 여객 예상 대기시간 | `estimateNextArrivalWaitSec` | Q0와 시나리오 처리능력에 따라 달라진다. 현행은 Q0>0이면 `(Q0+1)/C×3600`, Q0=0이면 0, C=0이면 산정 불가다. |
| 정상상태 이론 평균 대기시간 | `analyzeErlangC` | 안정 조건·모델 가정이 필요하다. 현재 적체가 언제 해소되는지를 직접 나타내지 않으므로 fluid 해소시간을 대체하지 않는다. |

### 6.2 신규 여객 예상시간을 목표로 선택할 경우의 구현안

이 절은 **확정 정책이 아니라 기존 계산과 연결 가능한 설계안**이다. 관측 평균 대기시간을 목표로 확정하면 그대로 적용하지 않는다.

단위를 `W*`: 초, `λ / μ / C`: 명/시간, `H`: 목표 해소 초로 두고 `C(s)=s×μ`라 한다.

1. 기존 `(Q+1)` 규칙과 Q=0 특례를 유지한다면, `C(s)>0`인 시나리오의 정수 허용 인원은 `Q*(s)=max(0, floor(C(s)×W*/3600−1))`로 환산할 수 있다. `Q/C` 정의를 선택한다면 다른 공식이므로 둘을 섞지 않는다.
2. `clearOf(s)`마다 `Q*(s)`를 다시 계산한다. 현재 수량에서 환산한 `Q*`를 추천 수량·COUNT 수량·최대 보유 수량에 그대로 쓰지 않는다.
3. 기존 인원 목표 fluid 계산을 유지한다면 `max(0,Q0−Q*(s))/(C(s)−λ)×3600`으로 계산한다. 이는 시간 상한을 정수 Queue 목표로 보수적으로 환산하는 방식이다. 이미 목표 이하이면 0, 초과하면서 배수율이 0 이하이면 `UNREACHABLE`이다.
4. 추천은 각 후보 수량의 `clearOf(s)`가 H 이내인지 평가해 최소 충족 수량을 찾는다. 기존 고정 `Q*`용 `estimateRequiredServerCnt` 공식을 그대로 호출하지 않는다. 탐색 상한·표현 범위·실패 경로를 정하고 단조성을 검증한다.
5. 기존 안정 하한 `floor(λ/μ)+1` 정책을 유지한다면 양의 유입에서 함께 적용한다. λ=0·시설 0개·빈 Queue 조합은 별도 정책으로 다룬다. 시간 목표라고 무조건 0개 추천을 허용하지 않는다.
6. 추천 수량을 다시 평가해 `goalMet`를 계산한다. 시간 상한·허용 인원 환산·해소시간·사용 산식을 응답 근거에 일관되게 표시한다.

예: W*=600초, μ=60명/시간/개, Q0=150명, λ=300명/시간일 때 s=10이면 C=600, Q*=99명이지만 s=20이면 C=1200, Q*=199명이다. 전자는 약 612초 후 목표에 도달하고 후자는 즉시 목표 이하로 평가된다. **시간 상한은 같아도 수량 시나리오마다 목표 인원이 달라진다.** 운영 0개·처리율 미상은 이 환산식을 적용하기 전에 별도 처리한다.

관측 평균을 업무 기준으로 선택한다면 과거 평균을 미래 Queue로 즉시 환산할 수 없으므로, FIFO 미래 궤적을 다시 계산할지 또는 해소 목표에 별도 예측 지표를 둘지 결정해야 한다. `Little's Law`의 `Lq=λWq`도 정상성·동일 범위의 평균 조건을 확인하지 않고 슬롯 끝 Queue에 적용하지 않는다.

## 7. DB 사전 확인·적용 계획

저장소에는 `TN_PM_PSG_PRCS_GRD`의 DDL·시드가 없다. `cast-ddl.sql`의 `MIN_VL NUMBER(10,3)`는 **`TN_PM_SMLT_SRVC_ATRB`의 다른 컬럼**이므로 등급표 자료형의 근거로 사용할 수 없다.

실DB에서 다음을 확인한 뒤 변경 스크립트를 작성한다.

1. `ALL_TAB_COLUMNS`로 소유자 PMOWN, 테이블 `TN_PM_PSG_PRCS_GRD`의 `MIN_VL / MAX_VL` 자료형·precision·scale·nullable 확인.
2. 그룹 02/04의 전체 등급코드·MIN/MAX를 백업하고, 초/분 단위 및 승인된 시간 경계 확인. 기존 인원값을 시간값으로 그대로 재사용하지 않는다.
3. NULL·음수·역전·중복·겹침·공백·필수 등급 누락 및 단위 변환 후 정수 여부·int 범위를 검사. DB 자료형이 NUMBER여도 실제 값이 정수인지 별도로 확인한다.
4. 기준정보를 다른 프로그램이 공유하는지 조사. 저장소 밖 소비자가 있으므로 DB 컬럼 타입 변경은 별도 영향 확인 후 진행한다. Java 정수화가 DB NUMBER의 물리 타입 변경을 필수로 요구하는 것은 아니다.
5. 승인된 시간 기준값·단위 정규화·제약과 새 코드를 같은 전환 절차로 적용한다. 인원 기준 코드와 시간 기준 데이터가 섞이는 구간을 만들지 않는다.
6. 이전 코드와 이전 기준표를 함께 복원할 수 있게 백업·복구 절차를 준비한다. 현재 등급표로 과거 결과를 재판정하는 경로는 과거 실행 화면의 색상도 바뀔 수 있으므로 재현 정책을 확인한다.
