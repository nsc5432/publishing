## 1. 목표와 범위

카드의 상세 버튼을 누르면 화면 중앙에 시설 운영 검토 팝업을 연다. 선택한 터미널과 아일랜드/출국장을 유지하며 다음 두 가지 계산을 제공한다.

| 계산 방식 | 체크인카운터 | 출국장 | 비교 결과 |
|---|---|---|---|
| 시설 수 조정 | 배정 부스 수 변경 | 운영 보안검색대 수 변경 | 현재 조건과 조정 조건의 혼잡해소 예상 소요시간·시각 |
| 목표 해소시간 설정 | 목표시간 내 필요한 총 부스 수 | 목표시간 내 필요한 총 보안검색대 수 | 현재 운영 수량·추천 총수량·추가 필요 수량 |

- 계산은 **M/M/s를 전제로 구성한 동일 큐의 입력**과 기존 `java/cast/domains/queue` 클래스를 사용한다.
- 팝업은 운영 검토용이다. 실제 시설 배정 저장, 사용자 시뮬레이션 실행, CAST 요청 발행은 범위에 포함하지 않는다.
- 이번 변경은 상세 이벤트와 팝업에 한정한다. 기존 카드·맵·체크인 상세의 공용 Queue 및 추천 산식을 함께 교체하지 않는다.
  - **2026-10-17 대체됨**: 카드·맵·체크인 상세의 추천도 팝업과 같은 계산으로 바꿨다 → [2026-10-17-fclt-card-domain-queue.md](2026-10-17-fclt-card-domain-queue.md)
- 모든 기존 DTO 필드명, enum 값, className, CSS 변수, DOM id를 유지하고 필요한 계약과 스타일만 추가한다.
- 이 문서의 신규 파일명·API명은 구현 제안이다. 이미 존재하는 계약은 변경하지 않는다.

### 2.1 M/M/s와 혼잡해소 시간의 구분

**Erlang C의 평균 개인 대기시간 `Wq`는 현재 쌓인 대기열의 혼잡해소 시간과 다른 지표다.**

이번 구현은 PPT와 기존 클래스에 맞춰 다음 조합을 사용한다.

| 목적 | 재사용 계산 | 해석 |
|---|---|---|
| 정상상태 분석 | `analyzeErlangC` | M/M/s의 대기확률, 평균 개인 대기시간, 평균 대기인원 |
| 현재 큐의 목표인원 도달 예상 | `estimateClearTimeSec` | λ·μ·시설 수가 유지되는 배수율 기반 **유입/처리 차이 계산** |
| 목표시간 내 필요한 총수량 | `estimateRequiredServerCnt` + 안정성 정책 | 유입/처리 차이 계산 목표를 만족하면서 M/M/s 안정조건을 충족하는 수량 |

주 결과를 “Erlang C로 계산한 정확한 대기열 소멸시간”이라고 설명하지 않는다. UI의 계산 기준에 **“M/M/s 가정 · 혼잡해소 시간은 유입/처리 차이 계산”**를 표시한다. 최초 구현은 시설 수가 즉시 바뀌고 예측 구간 동안 λ·μ가 일정하다는 가정이다. 개방 리드타임, 시간대별 수요 변화, 목표 달성 확률, 비정상상태의 확률적 최초도달시간은 제공하지 않는다.

엄밀한 M/M/s 과도상태 분석 또는 “95% 확률로 10분 내 해소”가 추가 요구되면 별도 계산기와 초기 상태 정의가 필요하다. 기존 해소시간 메서드를 이름만 바꿔 대응하지 않는다.

M/M/s 정상상태는 `ρ=λ/(sμ)<1`을 요구하고, `μ`는 시설 하나의 처리율이다. 독립적인 이론 확인 근거: [MIT Queueing models, PDF 15·30·31쪽](https://web.mit.edu/1.041/www/lectures/L8-queuing-models-2026sp.pdf).

## 3. 디자인 시안

[조작 가능한 기존 팝업 시안 열기](assets/2026-10-13-fclt-card-queue-popup.html)

시안은 기존 대시보드의 보라색 강조색, 둥근 패널, 옅은 배경을 따른다. HTML은 이전 대화에서 만든 시안을 보관한 **예시 계산용 참고물**이다. 실데이터나 기존 Java 계산기에 연결되어 있지 않다. HTML 내 단순 계산식을 운영 코드에 옮기지 않는다. 실제 구현에서는 아래 사양이 우선한다.

### 3.1 공통 구성

```text
┌──────────────────────────────────────────────────────┐
│ 시설 운영 검토                                     × │
│ 혼잡해소 시뮬레이션                                   │
│ T1 · 체크인카운터 · C 아일랜드                         │
│ 현재 시각 14:00       계산 기준 2026-10-13 14:00       │
├──────────────────────────────────────────────────────┤
│ 현재 배정 부스 8개       현재 조건의 해소 예상 30분 후  │
│                         해소 예상 시각 14:30          │
│ [부스 수 조정]             [목표 해소시간 설정]        │
├─────────────────────────┬────────────────────────────┤
│ ① 배정 부스 수           │ ② 조정 후 혼잡해소 예상     │
│ [−]       10개       [+] │          15분 후             │
│ ━━━━━━━━━━━━━━━          │ 해소 예상 시각 14:15         │
│ 0개            보유 10개│ 현재 조건보다 15분 단축      │
│ 현재보다 2개 추가 배정   │                              │
├─────────────────────────┴────────────────────────────┤
│ 소요시간 비교     현재 30분 / 조정 후 15분              │
│ 계산 기준 ▸ M/M/s 가정 · 혼잡해소 시간은 유입/처리 차이 계산       │
├──────────────────────────────────────────────────────┤
│ 운영 검토용                                    [닫기] │
└──────────────────────────────────────────────────────┘
```

목표시간 탭은 입력 영역을 `목표 혼잡해소 시간 [−] 10분 [+]`으로 바꾼다. 결과 영역에는 **추천 부스 총 12개 / 현재 8개 / 추가 4개 필요 / 보유 10개 초과**를 함께 표시한다. 위 수치는 §9의 Java 예제와 동일한 검증용 값이다.

출국장은 같은 레이아웃에서 다음 문구와 대상만 바뀐다.

| 항목 | 체크인카운터 | 출국장 |
|---|---|---|
| 대상 | 선택 아일랜드 | 선택 출국장의 보안검색 큐 |
| 현재 수량 | 현재 배정 부스 | 현재 운영 보안검색대 |
| 입력/탭 | 배정 부스 수 / 부스 수 조정 | 운영 보안검색대 수 / 보안검색대 수 조정 |
| 추천 | 추천 부스 수(총) | 추천 보안검색대 수(총) |

### 3.2 입력·결과 규칙

- 팝업의 초기 수량은 실제 계산 컨텍스트의 현재 운영 수량이다. 이전 시안처럼 미리 늘린 예시 수량으로 시작하지 않는다.
- 수량은 0 이상 정수이며 확인된 배정가능 최대수량까지 조정한다. 최대수량이 없으면 수량 조정은 비활성화하고 사유를 표시한다. 목표시간 추천 자체는 필요한 입력이 있으면 제공한다.
- 목표시간은 분 단위 양의 정수다. 기본값·상한은 서버 정책으로 제공한다. 초기 제안은 기본 30분, UI 조정 범위 1~120분이며 데이터의 유효 예측 범위에 맞춰 확정한다. 기존 시안의 5~90분을 계약으로 고정하지 않는다.
- 입력창·증감 버튼·슬라이더는 같은 값을 공유한다. 빈 입력/범위 밖/소수 입력에는 인라인 검증을 하고 계산 요청을 보내지 않는다.
- 수량 탭은 현재/조정 후 해소시간과 단축·증가분을 보여준다. 목표시간 탭은 현재/추천 총수량과 추가 필요량을 보여준다.
- 추천 총수량이 보유량을 초과해도 값을 자르지 않는다. “보유 수량으로 목표 달성 불가”를 별도로 표시한다.
- `0분`은 “이미 목표 인원 이하”, 산정 불가는 `—`, 용량 부족은 “현재 조건에서 해소 불가”로 구분한다.
- 추가 필요량은 `max(추천 총수량−현재 운영수량, 0)`이다. 추천이 현재보다 작으면 감소 가능 수량을 별도 문구로 표시한다.
- 대기인원 목표 `Q*`는 계산 기준 영역에 “대기인원 N명 이하 기준”으로 표시한다. 최초 범위에서 사용자가 이 값을 편집하지 않는다.
- 보조 “계산 기준” 영역에는 관측구간·데이터 출처·추정 여부와 정상상태 대기확률/평균 대기시간을 표시한다. Erlang C 지표를 혼잡해소 시간과 같은 라벨로 보여주지 않는다.
- 계산 중에는 결과 영역을 로딩 상태로 바꾸고 이전 결과를 새 입력의 결과처럼 표시하지 않는다. 오류 시 입력은 유지한다.
- 실제 화면에는 시안 상단의 “체크인카운터/출국장” 미리보기 전환기를 넣지 않는다. 클릭한 카드가 팝업 종류를 결정한다.

### 3.3 시각·배치·접근성

- 현재 시각은 Asia/Seoul 기준으로 표시한다. **계산 기준시각은 선택한 데이터의 Queue 스냅샷 시각**이며 현재 시각과 별개다.
- 해소 예상시각은 `계산 기준시각 + 해소 소요시간`이다. 과거/미래 조회에 현재 벽시계 시각을 더하지 않는다.
- 데이터가 과거인 경우 “계산 기준 대비 N분 후”라고 표시한다. 자정을 넘으면 날짜 또는 “다음 날”을 표시한다.
- 슬롯 조회 `hhmm`가 구간 시작이라면 마지막 Queue의 시각과 다를 수 있다. 서버 어댑터가 실제 스냅샷 시각을 반환하며 화면이 임의로 30분을 더하지 않는다.
- 폭은 약 640px을 기준으로 하고 좁은 화면에서 입력/결과를 세로 배치한다. 낮은 화면은 팝업 내용 영역만 스크롤하고 닫기 버튼은 접근 가능하게 유지한다.
- 대시보드 `.main`에는 `zoom`, `.app`에는 overflow 제한이 있으므로 **`document.body` portal + fixed backdrop**으로 뷰포트 정중앙에 배치한다.
- 일반 Dialog 용도로 구현한다. 기존 확인용 `AlertDialog`를 복잡한 입력 폼으로 전용하지 않는다. 일반 Dialog 도입 여부는 구현 첫 단계에서 결정한다.
- 제목 연결, 초점 이동·트랩, ESC 닫기, 배경 포커스/스크롤 차단, 닫을 때 상세 버튼으로 초점 복귀를 구현한다. 기존 `useModalDismiss`는 Tab 초점 트랩까지 제공하지 않는다.

### 5.2 λ·μ와 가정 확정

1. 같은 큐·시간범위의 직접 관측 유입률을 우선 사용한다.
2. 보존식으로 추정할 때는 `유입인원 = Qend−Qstart+서비스 시작인원`, `λ = 유입인원 / 구간초 × 3600`을 사용한다. `estimateArrivalPsgCnt(context)`를 활용하고 음수/결측/구간 불일치를 구분한다.
3. **처리 완료인원은 서비스 시작인원과 다르다.** 완료인원만 있다면 처리 중 인원 변화까지 확보하여 `유입 = ΔQ + Δ처리중인원 + 완료인원`으로 구성하거나 미산출로 남긴다. 완료인원을 무조건 시작인원 필드에 넣지 않는다. PPT의 간략 보존식을 실제 Queue 경계에 맞게 해석한다.
4. 외부 λ를 얻지 못한 경우에만 같은 모집단·같은 구간의 시간평균 `Lq`와 평균 `Wq`로 Little's Law를 적용한다. `littleLawApplicable` 조건을 확인한다. `Wq=0`을 λ=0으로 변환하지 않는다.
5. `estimateArrivalRatePerHour`는 외부 λ 또는 Little's Law를 사용한다. 보존식 결과가 자동 fallback으로 연결된 것으로 가정하지 말고 어댑터에서 명시적으로 연결한다.
6. λ·μ·Q0·Q*·기준시각을 한 번 확정한 컨텍스트로 현재/조정 시나리오를 비교한다. 조정된 Erlang C 대기시간으로 λ를 다시 역산하지 않는다. 시설 수 변경을 근거로 μ도 임의 변경하지 않는다.
7. `sharedHomogeneousServers`, `constantRates`, `erlangCApplicable` 등은 서버의 원천/모형 정책에서 설정한다. 프런트 요청값을 신뢰하거나 모든 시설에 무조건 true로 지정하지 않는다. `erlangCApplicable=true`는 적용 가정의 선언이며 통계적 검증 완료 표시가 아니다.

M/M/s 적용 조건은 포아송 도착, 독립적인 지수 서비스시간, 동일 평균 처리율의 병렬 시설, 동일 공용 큐, 선착순 처리, 무한 대기공간, 이탈 없는 모델이다. 시설/시간대에 이 전제를 적용할 수 없으면 이유를 반환한다. 관측값 자체와 “이미 목표인원 이하” 같은 직접 판정은 모델 적용 여부와 구분해 보여준다.

### 5.3 시설별 어댑터

**체크인카운터**

- 기존 `CastChknQueueService.retrieveChknQueueDay` 및 `ChknQueueDay/Slot/Series`의 공용 Queue를 입력 원천으로 재사용한다. 유인 카운터 `CC`만 대상으로 한다.
- 카드 표시 `oprCnt`는 시설 마스터 값인 반면, 실제 배정 부스는 `slot.getOprBoothCnt()` 경로다. 후자와 실행·운영 조건이 일치하는 수량을 사용한다.
- 30분 마지막 Queue, 60분 rolling 처리량, 시설 마스터 운영수를 서로 다른 기준인 채로 섞지 않는다. 어댑터는 관측구간과 Queue 시점을 명시한다.
- 기존 공용 Queue를 분해하거나 다른 화면의 계산을 바꾸지 않는다. 다만 실제 전용 부스 제약으로 공용·동질 시설 가정을 만족하지 못하는 대상에는 신규 M/M/s 분석 불가 사유를 표시한다.

**출국장**

- 카드의 대기인원은 `LGT+SC+SR`, 기존 추천 계산의 대상은 `SC+SR`이다. 카드 표시 합계를 그대로 보안검색 Queue로 사용하지 않는다.
- `SC/SR`의 실제 코드 의미, 서비스 단계, 중복 인원, 큐의 공유 관계를 확인하여 **보안검색대가 처리하는 동일 큐**를 구성한다. 서로 직렬인 단계를 병렬 서버 한 묶음으로 합산하지 않는다.
- `retrieveScrtyOpenCountList`와 실행 설정의 `FcltyOpngScrtyCntrlRsrcId` 경로를 확인해 같은 시점의 운영 보안검색대 수를 구한다. 카드 마스터 `totCnt/oprCnt`를 검증 없이 재사용하지 않는다.
- 기존 `getServiceRate`의 관측 처리량/시설 수 추정은 포화 여부에 따라 잠재 처리율과 다를 수 있다. 실제 서비스시간으로 μ를 구성하는 경로를 우선하고, 처리율 자료만 있으면 출처·적용 가정을 확인한 뒤 `avgPrcsTimeSec=3600/μ`로 변환한다. 근거가 없으면 미산출로 남긴다.

**Xovis 연계 시**

- PPT의 활성 Desk 조건은 같은 시각·island·queue에 속하고 `DeskOpen=1`, 유출속도>0인 시설이다. CAST 배정 수량에 이 조건을 그대로 덮어쓰지 않는다.
- 양의 유출속도를 보인 시설의 평균이 전체 처리능력을 대표하는지 검증한다. 관측 throughput과 서비스율을 혼동하지 않는다.
- `FacilityQueueExample`의 L 아일랜드 누적값 보정 TODO는 구현된 기능이 아니다. 시계열 정렬·중복·누락·누적 초기화/정정 처리를 별도 검증한다.
- 이번 대시보드 팝업은 먼저 CAST 원천으로 연결한다. Xovis 실조회·보정 파이프라인 전체 개발은 별도 범위이며 같은 Metrics/Context로 연계할 수 있게 어댑터 경계를 둔다.

### 5.4 목표인원 Q*

`Q*`는 해당 터미널·시설·지표에 맞는 혼잡등급 기준정보(`TN_PM_PSG_PRCS_GRD`, `CgnGradeScale`, `CastCgnGradeService`)에서 목표 혼잡등급의 허용 대기인원으로 결정한다. 해소를 의미하는 등급과 경계 포함 여부를 구현 전 확인한다. 예를 들어 기준이 `Q < N`이면 정수 인원 목표는 `N−1`이다. 기준이 없거나 겹치거나 보안검색 큐 범위와 맞지 않으면 사유를 반환하며 10명·220명 등으로 대체하지 않는다.

## 6. 계산 절차

### 6.1 시설 수 → 혼잡해소 예상

```text
μh = 3600 / avgPrcsTimeSec
ΔQ = max(0, Q0 − Q*)
drainRatePerHour = s × μh − λh

ΔQ = 0                     → 해소시간 0초 (이미 목표 이하)
ΔQ > 0, drainRatePerHour ≤ 0 → 현재 조건에서 해소 불가
그 외                      → clearTimeSec = ΔQ / drainRatePerHour × 3600
```

서비스는 같은 Metrics에 대해 현재 `s0` Context와 조정 `s1` Context를 만들고 각각 `estimateClearTimeSec(context, Q*)` 및 `analyzeErlangC(context)`를 호출한다. 각 Context의 λ·원천·가정은 동일하며 `oprServerCnt`만 달라진다. 기존 클래스는 불변이므로 builder 복사 구성용 헬퍼를 서비스 내부에 둔다.

### 6.2 목표시간 → 추천 총수량

```text
targetTimeSec = 입력 분 × 60
sFluid = estimateRequiredServerCnt(currentContext, Q*, targetTimeSec)
       = ceil((λh + ΔQ × 3600 / targetTimeSec) / μh)

sStableMin = λh > 0 ? floor(λh / μh) + 1 : 0
reqCnt = max(sFluid, sStableMin)
additionalCnt = max(reqCnt − s0, 0)
capacityFeasible = reqCnt ≤ 해당 큐의 배정가능 최대수
```

`sStableMin`은 **이번 팝업의 별도 추천 정책**이다. 기존 fluid 메서드의 반환 의미를 바꾸지 않는다. 특히 `Q0≤Q*`, `λ/μ`가 정수이면 기존 추천은 `ρ=1`이 될 수 있어, 양의 유입이 있을 때는 정상상태 안정성을 위한 한 개가 더 필요하다. λ=0이고 이미 목표 이하이면 기존 계약대로 0개 추천을 허용하며, s=0의 Erlang C는 산정 불가로 남긴다.

- 정책명(예: `STABLE_MMS_FLUID_TARGET`)과 안정성 하한 적용 여부를 응답 메타데이터로 전달한다. ρ=1 경계와 부동소수 오차 처리는 서버에서 검증한다.
- `estimateAdditionalServerCnt`와 `assessCapacityFeasibility`는 **기존 fluid 추천**을 기준으로 한다. 이를 최종 추천의 추가량·가능 여부로 무조건 쓰지 않는다. 최종 `reqCnt`에 안정성 보정이 있으면 최종값으로 다시 계산한다.
- 추천이 최대수량 이하일 때 추천 수량의 Context를 만들어 해소시간과 Erlang C 결과를 재검증한다. raw 초 기준으로 목표시간 이내인지 확인하며 표시 반올림으로 판정하지 않는다.
- 추천이 최대수량을 넘으면 총수량과 부족분을 그대로 보여주고 현실적인 조정 결과로 적용하지 않는다. `oprServerCnt > totServerCnt`인 Context는 생성하지 않는다. 필요하면 보유 최대수량의 Context로 달성 가능한 시간을 별도 계산한다.

### 6.3 Erlang C 참고지표

```text
a = λh / μh
ρ = a / s
WqSec = C(s,a) / (s × μh − λh) × 3600
LqTheory = λh × WqSec / 3600
```

`analyzeErlangC`의 기존 수치 계산을 사용하고 프런트나 서비스에 팩토리얼 기반 재구현을 만들지 않는다. `waitProbability`, `loadRatio`는 0~1 비율이며 화면에서만 ×100 한다. 관측 `avgQueuePsgCnt`를 이론 `LqTheory`로 덮어쓰지 않는다. `estimateServiceLevel`은 개인의 서비스 시작 확률이므로 전체 큐의 목표시간 달성 확률로 표시하지 않는다.

## 7. 팝업 전용 API 제안

계산의 단일 원본은 Java queue 클래스다. 프런트는 입력·단위 변환·표시만 맡는다. 초기 조회와 입력 변경 계산을 같은 전용 POST로 처리하여 현재/조정 결과를 항상 함께 반환한다.

```text
API_ENDPOINTS.DSBD_FCLT_QUEUE_SCENARIO (신규)
POST /pm/cast/smry/retrieveFcltQueueScenario
```

### 7.1 요청

| 필드 | 의미 |
|---|---|
| `smltId`, `ymd`, `hhmm`, `tmnlId` | 화면의 확정 조회조건. 서버에서 실행·일자·터미널 일치 확인 |

### 7.2 응답 구조

신규 DTO를 `api.types.ts`와 Java DTO에 추가한다. 기존 `DsbdFcltCardDto` 및 `FcltRecommendDto` 구조를 변경하지 않는다.

- λ·μ를 진단값으로 노출하면 기존 설계명 `arvlRate`·`srvcRate`는 **명/분** 계약을 유지한다. Java 명/시간 값은 응답 경계에서 ÷60 한다. 같은 이름을 명/시간으로 재정의하지 않는다.
- `current`: 현재 수량, `cgnClearMin`(반올림 전 분), 날짜 포함 `cgnClearDt`, 정상상태 참고지표.
- `scenario`: 입력 수량 또는 추천 총수량 `reqCnt`, 추가 필요량, 조정 후 `cgnClearMin/cgnClearDt`, 목표 충족/보유량 충족 여부, 정상상태 참고지표.
- 각 산출 지표의 메타데이터: 기존 `Computed`에서 얻은 `status`, `method`, `reason`. 원천 값이 null인 지표는 null을 유지한다.
- 추천 정책 메타데이터: raw fluid 추천, 안정성 최소수량, 최종 정책 적용 여부. 화면 본문에는 최종값을 표시하고 상세 근거에 차이를 남긴다.

`reqCnt`는 최종 **총 소요 수량**이다. `cgnClearMin`은 소요시간이며 날짜 포함 `cgnClearDt`는 별도 신규 필드다. 기존 카드의 `cgnClearTime(HHmm)` 형식을 바꾸지 않는다. 초/분 변환과 시각 덧셈은 서버에서 원래 정밀도로 처리한다. 화면에서 올림한 분을 다시 계산 입력으로 쓰지 않는다.

### 7.3 동일 입력 유지와 오류 처리

- `contextVersion`은 대상·원천 시각·관측값·λ·μ·운영/최대수량·Q*·정책 버전을 포함하는 정규화된 컨텍스트의 서버 생성 식별값이다. 사용자 입력 수량·목표시간은 포함하지 않는다.
- 재계산 시 서버가 동일 원천을 구성하고 버전을 대조한다. 달라졌으면 `CONTEXT_CHANGED` 같은 식별 가능한 오류를 반환해 기준정보 재조회를 유도한다. 바뀐 원천을 이전 기준값과 조용히 비교하지 않는다.
- 버전값은 권한 증명이 아니다. 매 요청마다 대상 접근과 입력을 검증한다. 새 영속 테이블은 필요하지 않으며 최초 구현에서 분산 캐시 의존성도 만들지 않는다.
- 빠른 입력 변경은 짧은 debounce(예: 250ms)로 합친다. 같은 값이어도 명시적인 재조회는 새 요청을 만들 수 있어야 한다.
- `useFetched`의 늦은 응답 폐기 패턴에 맞춰 대상·모드·수량·목표시간·버전을 요청 조건으로 둔다. 팝업 종료, 대상 변경, 탭 변경 이후의 이전 응답은 반영하지 않는다.
- 서버의 HTTP 200 본문 `error`도 `unwrap`을 거쳐 처리한다. 정상적인 `UNAVAILABLE/UNREACHABLE`은 통신 오류 알럿이 아니라 해당 결과의 상태로 표시한다.
- 프런트 화면 접근 정책을 유지하고 새 조회 API도 기존 역할 체계에 맞춰 서버 접근을 확인한다. 이 팝업에서 매출 정보는 조회하지 않는다.

## 8. 상태와 경계값

| 조건 | 기존 클래스 동작 / 팝업 처리 |
|---|---|
| `Q0≤Q*` | 해소시간은 다른 입력 검사 전에 `CALCULATED`, `DIRECT`, 0초. “이미 목표 이하” 표시. 안정적으로 계속 유지된다는 보장은 아님 |
| Q0·서비스시간·λ 등 필수 입력 부족 | 관련 지표 `UNAVAILABLE`, `—`와 사유. 원천 없음과 실제 0 구분 |
| 평균 대기시간 0, 외부 λ 없음 | Little's Law로 λ=0을 만들지 않음 |
| `Q0>Q*`, `sμ≤λ` | 해소시간 `UNREACHABLE`. 현재 조건에서 해소 불가 |
| `λ≥sμ` | Erlang C는 `UNAVAILABLE`. 해소시간의 `UNREACHABLE`로 일괄 치환하지 않음 |
| 운영수 s=0 | 용량 0은 직접 계산 가능. Erlang C는 산정 불가. 남은 큐가 있으면 배수율에 따른 처리 |
| 추천>배정가능 최대수 | 추천값 유지, 보유량 충족 false. 보유량으로 잘라서 목표 달성처럼 보이지 않음 |
| 최대수량 없음 | 보유량 충족 여부 미산출. 수량 슬라이더 임의 상한 금지 |
| 모형 가정 미충족 | 모델 계산 미산출, 해당 사유 표시. 숫자를 만들기 위해 플래그 자동 true 금지 |
| 목표시간≤0, 소수 수량, 음수, NaN, Infinity | 요청 검증 오류. builder 예외를 내부오류로 방치하지 않음 |
| 정수 범위 초과/수치 오버플로 | 원래 상태를 보존해 미산출 표시 |
| 긴 해소시간/다음 날짜 | 실제 수치를 유지. 표시 공간 때문에 99분 등으로 자르지 않음 |

## 9. 검증 계획

### 9.1 계산 검증 벡터

`FacilityQueueExample`의 입력을 assertion 검증으로 옮겨 실제 백엔드 테스트 환경에서 실행한다. 단순 콘솔 출력만으로 통과 판정하지 않는다.

공통: λ=180명/시간, 평균 서비스시간 120초 → μ=30명/시간/시설, Q0=40, Q*=10, 현재 s=8, 최대수량=10.

| 시나리오 | 기대 결과 |
|---|---|
| 현재 수량 8 | 해소 1,800초=30분, ρ=0.75 |
| 수량 10으로 조정 | 해소 900초=15분, 현재보다 15분 단축 |
| 목표 10분 | 추천 총12개, 추가4개, 보유10개로 달성 불가 |
| 수량 6 | 해소 `UNREACHABLE`, Erlang C `UNAVAILABLE` |
| Q0=Q*=10, λ=180 | 현재 해소 0초, raw fluid 추천6, 안정성 정책 최종7 |
| Q0≤Q*, λ=0 | 해소0초, 필요수량0 허용, s=0 Erlang C 미산출 |

Erlang C는 독립적인 소규모 기준값도 대조한다. 예를 들어 s=1, λ=30명/시간, μ=60명/시간이면 ρ=0.5, 대기확률0.5, Wq=60초, Lq=0.5명이다. λ=0, ρ가 1에 가까운 안정 상태, 큰 s의 수치 안정성도 확인한다.

추가 검증:

- 같은 원천에서 s가 증가할 때 유효 해소시간이 증가하지 않는지 확인한다.
- 양의 backlog에서 목표시간을 줄일 때 최종 추천 총수량이 줄지 않는지 확인한다.
- 추천 수량의 raw 해소시간이 목표 이내인지, 양의 λ에서 `ρ<1`인지 확인한다.
- Q0/시간평균 Queue 혼용, 초↔분↔시간 60배 오류, 비율↔백분율 오류를 검증한다.
- 시작인원과 완료인원이 다른 fixture, 중복/누락 관측, 큐별 모집단 불일치에서 무리한 fallback이 없는지 확인한다.
- λ·μ가 시설 수 조정에 따라 변하지 않고 같은 원천 버전이 유지되는지 확인한다.
