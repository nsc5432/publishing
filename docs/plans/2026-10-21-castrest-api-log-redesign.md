# CAST REST API 로그 재설계 계획

작성일: 2026-10-21

상태: D1~D6 기반 참조 사본 구현·로컬 검증 완료. 실제 백엔드·Oracle·CAST 통합 검증과 구 테이블 제거는 미완료.

대상: `CastRestController`의 POST API 3종

## 1. 목표와 범위

- `REQ_GetResourceInformation.do`, `REQ_GetResource.do`, `REQ_SetResource.do`의 요청·응답·오류를 DB에 저장한다.
- API Type은 `GetResourceInformation`, `GetResource`, `SetResource`다.
- MSG Type은 `payload`, `result`, `errorMsg`다. 대소문자를 포함해 이 값을 그대로 사용한다.
- 별도 설정 테이블에서 API Type × MSG Type의 9개 조합을 각각 Y/N으로 제어한다.
- 오류 저장 호출을 개별 실패 지점에 흩어 놓지 않고 공통 실행 경계에서 관리한다.
- `TT_PM_CASTREST_REQ_DEBUG`를 신규 구조로 대체하고 최종적으로 제거한다.
- 물리 명칭은 루트의 `표준단어.txt`를 우선 적용한다.

최초 문서 작성 단계는 계획만 다뤘다. 후속 구현 진행 범위는 §10에 기록하며 프런트엔드 변경은 없다.
GET `_Test` API는 사용자가 지정한 세 POST API 범위에 포함하지 않는다.

기존 Debug 테이블의 CREATE DDL은 저장소에 없다. 실제 DB의 테이블 정의·제약조건·권한·외부 사용처는 아직 확인하지 않았다.

### 3.3 D6 적용 방식: 기존 계속 처리 유지

대상은 로그 파일이 아니라 CAST 모델 내용을 읽거나 저장하는 업무 파일이다. 현재는 일부 파일 읽기·쓰기 IOException을 catch한 뒤 실행 단계 로그만 남기고 후속 처리를 계속한다. 따라서 읽기 실패 후 빈 모델 내용으로 응답을 만들거나, 쓰기 실패 후에도 파일 관련 DB 처리를 계속할 수 있다.

| 구간 | 확정 동작 |
|---|---|
| 파일 읽기 실패(GetResource) | 현재처럼 후속 응답 생성 계속 |
| 파일 쓰기 실패(SetResource) | 현재처럼 후속 DB 처리 계속. 해당 파일 오류만으로는 롤백하지 않음 |
| 오류 정보 전달 | 기존 구체 IOException catch에서 원인 예외를 요청 단위 내부 결과에 수집. DB 저장 메서드는 호출하지 않음 |
| 오류 저장 | 공통 경계에서 errorMsg Y일 때 원인·전체 스택을 한 건으로 저장 |

업무가 계속 진행되어 정상 응답이 반환되어도 수집된 파일 오류가 있다면 errorMsg를 저장한다. 이후 별도의 중단 예외가 발생하면 앞서 수집된 파일 오류와 마지막 예외를 함께 기록한다. 오류 수집 자체가 기존 성공/실패 판정이나 DB 커밋 여부를 바꾸지 않도록 한다.

스위치 N은 DB 오류 로그 적재만 끈다. 업무 오류의 중단/계속 여부를 스위치로 바꾸지 않는다. 이미 일부 기록된 파일이나 기존 파일의 덮어쓰기는 DB 롤백으로 복구되지 않는다. 신규 로그 저장 자체의 실패는 D3에 따라 업무를 중단하지 않는다.

## 4. DB 구조 권고안

### 4.1 표준단어 적용

| 한글 | 표준 약어 | 사용 예 |
|---|---|---|
| API / 유형 / 코드 | API / TYPE / CD | CAST_API_TYPE_CD |
| 메시지 / 유형 / 코드 | MSG / TYPE / CD | CAST_LOG_TYPE_CD |
| 로그 / 설정 | LOG / STNG | TN_PM_SMLT_CAST_LOG_STNG |
| 사용 / 여부 | USE / YN | USE_YN |
| 로그 / 내용 | LOG / CN | LOG_CN |
| 최초 / 등록 / 일시 | FRST / REG / DT | FRST_REG_DT |
| 최종 / 수정 / 일시 | LAST / MDFCN / DT | LAST_MDFCN_DT |

`CASTREST`는 기존 연계 모듈 식별어를 유지한 것이다. `TN`·`TH` 접두사는 저장소의 기존 테이블 관례를 따른다. 아래 물리명·길이는 제안이며 실제 DB 명명 규칙과 대조한 뒤 확정한다.

### 4.2 설정: PMOWN.TN_PM_SMLT_CAST_LOG_STNG

한 행은 하나의 API Type × MSG Type 조합이다. 초기 데이터는 반드시 9행을 제공하며 USE_YN은 모두 N이다. 설정 행이 누락된 조합도 N으로 처리한다.

| 컬럼 | 자료형 제안 | 제약·의미 |
|---|---|---|
| CAST_API_TYPE_CD | VARCHAR2(30 CHAR) | PK 1. 지정한 API Type 3종 |
| CAST_LOG_TYPE_CD | VARCHAR2(10 CHAR) | PK 2. payload/result/errorMsg |
| USE_YN | CHAR(1 CHAR) | NOT NULL, DEFAULT 'N', CHECK Y/N |
| FRST_REG_DT | TIMESTAMP(6) | NOT NULL, DEFAULT CURRENT_TIMESTAMP |
| LAST_MDFCN_DT | TIMESTAMP(6) | 설정 수정 시 명시적으로 갱신 |

API·메시지 유형에도 CHECK 제약을 둔다. 관리 화면 없이 DB에서 직접 변경한다면 수정일시도 운영 SQL에서 함께 갱신한다. 변경자 컬럼의 필요 여부는 실제 DB 공통 감사 컬럼 정책과 대조한다.

조회는 요청 시작 시 해당 API의 3행을 한 번에 읽고 요청 동안 같은 설정을 사용한다. 처리 중 설정이 바뀌어도 한 호출 안에서는 시작 시점의 설정을 유지한다. 다음 요청은 변경된 설정을 읽는다.

설정은 업무 트랜잭션을 오염시키지 않는 별도 읽기 경계에서 조회한다. 조회 실패 시 본처리는 계속하고 그 요청의 신규 DB 로그는 모두 생략하며 서버 파일 로그에 조회 실패를 남긴다. 다른 요청의 설정을 대신 사용하지 않는다.

### 4.3 로그: PMOWN.TH_PM_SMLT_CAST_LOG

한 행은 한 메시지다. 정상 요청은 활성 설정에 따라 payload/result 최대 2행, 실패 요청은 payload/result/errorMsg 최대 3행이다. result는 실제 생성된 응답이 있을 때만 저장한다.

| 컬럼 | 자료형 제안 | 제약·의미 |
|---|---|---|
| CAST_API_TYPE_CD | VARCHAR2(30 CHAR) | NOT NULL. API Type |
| CAST_LOG_TYPE_CD | VARCHAR2(10 CHAR) | NOT NULL. MSG Type |
| LOG_CN | CLOB | 요청·응답 원문 또는 오류 상세 |
| FRST_REG_DT | TIMESTAMP(6) | NOT NULL, DEFAULT CURRENT_TIMESTAMP |

- API·메시지 유형 CHECK 제약만 두며 로그 테이블에 PK·UNIQUE 제약과 채번 시퀀스를 두지 않는다. 실행기는 같은 요청의 동일 유형을 한 번만 기록한다.
- 2026-10-22 결정에 따라 로그는 위 네 컬럼만 저장한다. 호출 연결 키가 없어 동시 호출의 요청·응답·오류를 정확히 짝지을 수 없으며 동일 등록일시의 행 순서는 보장하지 않는다.
- 시간 조건 검색·정리를 위한 FRST_REG_DT 인덱스를 기본으로 검토한다. API별 대량 조회용 추가 인덱스는 실제 조회량을 보고 결정한다.
- 설정 행 삭제나 스위치 변경 때문에 과거 로그를 지울 수 없도록 설정 테이블에 FK를 걸지 않는다.
- payload/result는 재직렬화·가공·임의 절단 없이 Java에서 받은 요청 문자열과 반환할 응답 문자열을 저장한다. HTTP 바이트 원문이나 전송 완료를 증명하는 로그는 아니다.
- payload가 N이어도 result/errorMsg를 독립 저장할 수 있다. 로그 전용 요청 부모 테이블은 두지 않는다.
- 한 요청에서 발생한 복수 오류는 공통 결과 객체에 모아 errorMsg CLOB 한 건으로 기록한다. 정상적으로 오류가 없으면 errorMsg 행을 만들지 않는다.
- 오류 정보만 필요한 경우 payload를 errorMsg에 복사하지 않는다. 꺼진 payload/result를 오류 로그로 우회 저장하지 않는다.
- 초기안은 전문 전체를 CLOB에 저장한다. 실제 최대 전문 크기·보관기간에 따른 저장량을 검증하고, 마스킹이나 상한이 필요하다면 명시적으로 정책을 추가한다.

## 5. 메시지별 저장 규칙

| 상황 | payload Y | result Y | errorMsg Y |
|---|---|---|---|
| 정상 처리 | 수신 문자열 | 실제 반환할 정상 응답 | 저장 안 함 |
| 파일 오류 수집 후 정상 응답 | 수신 문자열 | 기존 흐름에서 생성한 정상 응답 | 수집한 파일 예외의 원인·전체 스택 |
| 실패 응답 생성 가능 | 수신 문자열 | 실제 반환할 실패 응답 | 예외 상세 또는 명시적 실패 사유 |
| 응답을 생성하지 못하고 상위 전파 | 수신 문자열 | 응답이 없으므로 저장 안 함 | 공통 경계에서 포착한 오류만 저장 |
| 해당 유형 N | 저장 안 함 | 저장 안 함 | 저장 안 함 |

오류 없는 빈 응답과 업무 실패를 구분한다. XML 전체를 다시 파싱하거나 `contains("false")` 같은 문자열 검색으로 오류를 추측하지 않는다. 오류 분기는 내부 처리 결과에 실패 여부·사유를 명시하거나 구체적인 업무 예외로 전파한다. 외부 XML 형식에 로그용 필드는 추가하지 않는다.

예외의 errorMsg는 API 유형·예외 클래스·메시지·원인 체인·전체 스택을 포함한다. 예외 없이 발생한 업무 실패에는 실패 사유를 기록하며 가짜 스택을 만들지 않는다. 예외와 오류 응답 모두를 기록한다는 D2의 확정 정책을 따른다.

## 6. 공통 실행·오류 처리 구조

### 6.1 책임 배치

1. 컨트롤러의 세 POST 메서드는 API 유형·payload·업무 호출을 공통 실행기 `CastRestApiExecutor`에 전달한다.
2. 공통 실행기는 설정 조회, payload 적재, 업무 호출, 실패 처리, result/errorMsg 적재를 담당한다.
3. 업무 호출은 별도 Spring 서비스 프록시를 통과한다. 실행기 바깥으로 커밋/롤백 결과가 돌아온 뒤 응답 로그를 저장한다.
4. 중단해야 하는 업무 실패는 명시적인 실패 결과 또는 구체 예외로 공통 실행기에 전달한다. D6의 계속 처리 대상 IOException은 기존 catch에서 요청 단위 내부 결과에 수집하고 실행을 계속한다. 개별 분기에서 DB 로그 저장 메서드를 부르지 않는다.
5. XML 생성은 기존 API별 응답 생성 책임을 재사용한다. GetResourceInformation 실패 XML, GetResource의 INVALID_REQUEST·unsupported resource 응답, SetResource 실패 XML을 각각 보존한다.

이름은 역할을 설명하기 위한 제안이다. 구현 시 공통 실행기의 입력·출력 타입과 기존 서비스 String/DTO 오버로드의 호환 어댑터를 먼저 확정한다. GET 테스트 경로가 같은 처리를 사용하더라도 대상 밖이라면 신규 DB 적재를 수행하지 않는다.

### 6.2 예외와 트랜잭션

- 공통 try 범위에는 XML 파싱뿐 아니라 기존 try 밖의 초기화·saveSimLog·업무 서비스 호출·트랜잭션 종료도 포함한다.
- 공통 catch는 XML/IO/업무/DB/트랜잭션의 구체 예외를 대상으로 구성한다. checked 예외는 원인을 유지한 전용 예외로 변환하거나 명시적으로 전달한다.
- AGENTS.md §5는 `Exception`·`RuntimeException`·`Throwable`·`NullPointerException`의 포괄 catch를 금지한다. 광범위한 try 영역과 구체적인 multi-catch를 조합하며 이 규칙을 그대로 따른다.
- 구체 예외 목록 밖의 예기치 않은 오류까지 모두 DB에 포착한다고 보장하지 않는다. 구현 전 실제 백엔드의 기존 전역 예외 처리를 확인해 연계 가능한 범위를 명시한다. D2에 따라 오류 기록 대상으로 보되, 해당 경로를 구현·검증하기 전에는 포착 완료로 판정하지 않는다. 응답을 임의로 성공이나 실패 XML로 덮지 않는다.
- SetResource는 실패 결과·예외 처리 모두 기존 DB 롤백 여부를 경로별로 확인한다. 기존 예외 처리의 rollback-only를 잃지 않도록 한다. 새롭게 롤백시키는 경로가 있다면 별도 동작 변경으로 명시한다.
- 업무 DB 변경의 롤백과 파일 시스템 변경의 복구는 다르다. 기존 파일 저장의 원자성을 이 로그 작업이 보장하지 않는다.
- D6 대상 파일 IOException은 기존 catch와 계속 처리 동작을 유지한다. 오류 수집용 컨텍스트를 내부 호출에 명시적으로 전달하고 업무 결과와 함께 공통 실행기로 돌려준다. 다른 예외로 업무 트랜잭션이 롤백되어도 수집한 오류를 참조할 수 있게 컨텍스트는 실행기가 소유한다. 오류를 다시 throw하거나 오류 수집만으로 rollback-only를 지정하지 않는다.

### 6.3 로그 장애 격리

- 로그 INSERT는 별도 Bean의 `REQUIRES_NEW` 메서드로 실행한다. 같은 객체 내부 호출로 트랜잭션 프록시를 우회하지 않는다.
- 저장 실패의 구체 예외는 트랜잭션 프록시 바깥의 공통 로깅 조정자가 처리한다. INSERT뿐 아니라 독립 로그 트랜잭션 커밋 실패도 포함한다.
- payload 적재 실패 후에도 업무를 호출하고, result/errorMsg 적재 실패도 API 결과를 바꾸지 않는다. D3의 확정 정책이다.
- 로그 저장 장애는 서버 파일 로그로만 알리고 새 DB errorMsg를 재귀적으로 저장하지 않는다. 알려진 DB 장애가 반복될 때 남은 로그 적재를 생략할지는 구현 시 한 요청 단위로 정한다.
- 동기 저장을 기본안으로 둔다. 별도 큐·스레드·비동기 재시도는 추가하지 않는다. REQUIRES_NEW와 동기 I/O가 연결 풀·응답시간에 미치는 영향은 실환경에서 확인한다.
- TH_PM_SMLT_EXCN_LOG의 기존 저장 실패는 업무 호출 오류와 신규 로깅 장애를 구분한다. 이번 스위치가 기존 단계 로그까지 제어한다고 해석하지 않는다.

## 8. 기존 테이블 제거와 전환

1. 실제 구 테이블의 정의·권한·동의어·외부 조회/배치를 확인한다. 구 데이터는 D5에 따라 폐기하며 신규 이관이나 데이터 백업을 이번 전환 작업에 포함하지 않는다. 구버전 앱 롤백에 필요한 테이블 정의·권한은 별도로 확보한다.
2. 신규 테이블·설정 9행과 권한을 먼저 적용한다.
3. 신규 코드 배포 후 각 유형의 로그 적재와 스위치 반영을 확인한다. 이 기간에는 구 테이블을 남겨 롤백 경로를 확보한다.
4. 구 테이블을 쓰는 구버전 인스턴스와 외부 의존성이 없음을 확인한 뒤 구 테이블을 제거한다. 무조건적인 DROP PURGE는 계획하지 않는다.
5. 제거 전 앱 롤백은 구 테이블을 사용한다. 제거 후 롤백에는 별도로 확보한 구 테이블 정의·권한으로 빈 구 테이블을 복구한다. 폐기한 구 로그 데이터는 복구 대상이 아니다. Oracle DDL을 업무 트랜잭션 롤백으로 되돌릴 수 있다고 가정하지 않는다.

구 데이터에는 API·MSG 유형이 없어 요청/응답을 신뢰할 수 있게 분류할 수 없다. 전문 내용을 추측해 신규 유형을 부여하는 자동 이관은 권고하지 않는다.

새 로그는 D5에 따라 보관기한을 두지 않고 수동으로 관리한다. 자동 삭제 배치와 보관일수 설정은 추가하지 않는다. 실제 삭제는 운영자가 필요할 때 기간·대상을 정해 수행한다.

## 9. 완료 기준과 검증

- 세 API 각각의 payload/result/errorMsg 독립 스위치를 확인한다. API별 8가지 Y/N 조합과 오류 유무를 검증한다.
- payload가 N인 상태에서도 result/errorMsg가 독립적으로 적재되는지 확인한다.
- 같은 요청은 설정 스냅샷을 공유하고 다른 요청·서버 인스턴스의 설정·오류 수집 상태와 섞이지 않는다. ThreadLocal 누수에 의존하는 설계를 피한다.
- 설정 변경은 D1에서 정한 시점에 반영되며, 누락·조회 실패는 D3/D4의 정책을 따른다.
- 잘못된 XML, 미지원 리소스, 없는 모델/PropertySet, 결과 미저장, 파일 I/O 실패, DB 오류와 트랜잭션 종료 실패를 검증한다.
- D6 대상 파일 읽기·쓰기 실패 후에도 기존 후속 처리·응답·DB 커밋 판정이 유지되는지 확인한다. 정상 응답과 errorMsg가 함께 저장되는 경우, errorMsg N인 경우, 수집 후 다른 중단 예외가 발생한 경우를 검증한다.
- 실패 응답의 result와 errorMsg가 각각의 스위치를 따르고 오류 상세가 중복 저장되지 않는지 확인한다.
- SetResource 실패 시 업무 데이터는 기존 계약대로 롤백되고 활성화된 신규 로그는 남는다. 로그 장애로 업무 커밋/롤백이 바뀌지 않는다.
- 초기화·saveSimLog 오류가 기존 try 밖에 있었다는 이유로 새 공통 경계에서 누락되지 않는지 확인한다.
- 대형 CLOB·한글·개행·XML 특수문자의 문자열 보존과 서버 응답 형식을 대조한다.
- GET 테스트·Delete API 및 기존 실행 단계 로그가 정한 범위대로 동작하는지 확인한다.
- 동시 요청과 대형 전문에서 DB 연결 풀·응답시간·저장량을 확인한다.
- 구 Debug 서비스·statement·테이블 참조가 남지 않는지 검색하고, 실제 DB에서 제거 완료를 확인한다.

이 저장소의 Java는 빌드 파일이 없는 참조 사본이다. 실제 백엔드 레포의 컴파일·PMD·통합 검증과 Oracle 검증 DB 확인을 완료해야 구현 완료로 판정한다. 프런트엔드 변경이 없어 React 타입체크·빌드는 실행하지 않는다.

## 10. 2026-10-21 후속 구현

세 POST에 공통 실행기와 요청 단위 컨텍스트를 연결하고, 별도 로그 매퍼·REQUIRES_NEW 서비스·설정/로그 DDL을 추가했다.
기존 Debug 서비스와 INSERT statement는 제거했다. 파일 I/O 계속 처리와 SetResource rollback-only는 보존했다.
구 테이블의 실제 DROP은 사용 종료 확인 후 수행하도록 분리했다.

적용 SQL·전환/복구 절차·오류 포착 범위와 검증 한계는 [CAST REST API 로그 적용·검증](../castrest-api-log.md)에 정리했다.
당시 추가한 로컬 검증 도구는 최신 구현과 맞지 않아 2026-10-22에 삭제했다. 검증은 실제 백엔드 레포와 Oracle 검증 DB에서 수행한다.
실제 백엔드/DB 접속 및 전역 예외 처리·트랜잭션 설정은 참조 사본에 없어 확인하지 못했다.
