## 1. 목적과 독자

사용자 시뮬레이션(What-if)의 취지와 설정 가능한 내용을 사업·검토 담당자에게 소개하는 별첨 문서를 만든다. 운항·여객 및 시설 운영 조건을 조정한 뒤 시뮬레이션으로 영향을 확인하는 기능의 목적과 절차를 설명한다.

개발 설명이나 상세 조작 매뉴얼보다 각 영역에서 무엇을 설정하고 어떤 목적으로 활용하는지를 중심으로 쓴다. API·DTO·DB·CAST 리소스 등 내부 구현 용어는 본문에 넣지 않는다.

## 2. 사용자 인터뷰 확정 사항

| 결정 항목 | 확정 내용 |
|---|---|
| 주 독자와 설명 수준 | 사업·검토 담당자용 기능 소개 |
| 주요 구성 | 날짜·터미널 선택 / 운항편·여객수 / 체크인카운터 / 출국장, 총 4단계 |
| 실행 이후의 범위 | 실행·모니터링·결과 확인을 짧게 정리하며 상세 조작 설명은 생략 |
| 예시 사용 | 가상 시나리오나 수치 예시 없이 기능과 절차만 설명 |
| 브라우저 화면 | 사용자가 나중에 삽입. 문서에는 위치·공간과 짧은 삽입 안내만 배치 |
| 참고 양식 적용 | 지정한 DOCX의 문서 서식을 기준으로 신규 별첨 작성 |

현재까지 추가로 사용자 결정이 필요한 항목은 없다. 분량·그림 크기·세부 소제목은 이 계획의 편집 기준으로 정하고, 실제 조판 결과에 맞춰 조정한다.

## 3. 문서 구성안

### 목차

참고 문서와 같은 목차 형식을 사용한다. 별도 장식 표지는 추가하지 않으며, 별첨 제목은 문서 제목 및 머리말에 반영한다.

### 1. What-if 시나리오 개요

- 사용자 시뮬레이션의 목적: 운영 조건 변화에 따른 여객 흐름과 시설 혼잡 영향을 사전에 검토하도록 지원한다.
- 설정 범위: 기준일자, 편집 대상 터미널, 여객수 조정, 체크인카운터 및 출국장 운영 조건.
- 활용 흐름: 대상 선택 → 조건 조정 → 실행 → 진행 상태 및 결과 확인.
- 기능 설명과 실제 시뮬레이션 결과를 구분하고, 검증하지 않은 효과나 개선 수치를 서술하지 않는다.

### 2. 사용자 시뮬레이션 설정 절차

아래 4단계는 초기 날짜·터미널 선택과 실제 화면의 3개 설정 탭을 연결한 설명 순서다. 실제 화면에 별도의 4단계 마법사가 있는 것처럼 표현하지 않는다. 단계마다 짧은 목적 설명, 설정 가능한 내용, 화면 삽입 공간 순으로 배치한다.

#### 2.1. 1단계 — 날짜 및 터미널 선택

- 기준일자를 지정하고 해당 날짜의 조건을 조회하는 기능을 안내한다.
- T1·T2 중 조건을 편집할 터미널을 선택해 시작하는 흐름을 설명한다.
- 터미널 선택은 편집 대상 선택이며, 실행에는 T1·T2 전체 조건을 사용한다는 점을 명확히 적는다.
- 화면 자리 S1을 배치한다.

#### 2.2. 2단계 — 운항편 및 여객수 조건 설정

- 시간대별 운항편·여객 현황, 차트 및 원래/변경 여객수 확인 기능을 소개한다.
- 전체 시간대 일괄 또는 시간대별로 여객수 조정 비율을 설정하는 기능을 설명한다.
- 비율 설정 범위는 -100~100%, 5% 단위이며, 조정 대상은 여객수다. 운항편 수 자체를 증감시키는 기능으로 설명하지 않는다.
- 조정값은 설정 기능의 범위로만 표기하고, 특정 값의 가상 적용 사례는 넣지 않는다.
- 화면 자리 S2를 배치한다.

#### 2.3. 3단계 — 체크인카운터 운영 조건 설정

- 아일랜드별 체크인카운터 현황과 편집 대상을 선택하는 기능을 소개한다.
- 부스 선택 및 항공사 배정, 1시간 단위 운영시간 설정을 설명한다.
- 키오스크와 셀프백드롭의 수량 설정을 같은 영역의 기능으로 설명한다.
- 적용·취소는 편집 내용을 정리하는 절차로 간단히 안내하고, 클릭·드래그 조작을 세세하게 나열하지 않는다.
- 화면 자리 S3을 배치한다.

#### 2.4. 4단계 — 출국장 운영 조건 설정

- T1 출국장 1~6, T2 출국장 1~2의 운영 조건을 설정하는 기능을 소개한다.
- 출국장 사용 여부와 1시간 단위 운영시간을 설정하는 내용을 설명한다.
- 일반 레인·스마트패스·보안검색대 수량 설정을 소개한다.
- 보안검색대 수량을 시간대별로 따로 계획하는 기능이 있는 것처럼 설명하지 않는다.
- 화면 자리 S4를 배치한다.

### 3. 시뮬레이션 실행 및 결과 확인

4단계 이후의 활용 흐름을 짧은 절로 정리한다. 별도의 5단계를 만들지 않는다.

1. 조건 확인 및 저장: 필요 시 `현재상태 저장`으로 설정을 보관한다. 실행 시 변경 조건이 함께 저장된다는 점을 간단히 안내한다.
2. 실행 및 모니터링: `시뮬레이션 실행` 후 모니터링 화면에서 진행 상태를 확인하는 흐름을 설명한다.
3. 결과 확인: 완료된 실행의 결과 화면에서 설정 조건에 따른 예측 결과를 확인하는 경로와 목적을 정리한다.

모니터링 필터·상태 코드·결과 화면별 상세 지표와 조작법은 생략한다. 현재 범위에서는 이 절에 별도의 화면 자리를 추가하지 않는다. 결과 화면으로 이동하는 명칭과 경로는 제작 시 모니터링 화면 구현을 대조한 뒤 확정한다.

## 4. 화면 삽입 공간 계획

실제 화면 캡처나 합성 화면은 제작하지 않는다. 나중에 이미지로 교체하기 쉬운 사각형 영역을 두고, 영역 안에 짧은 안내 문구를 보이는 본문으로 넣는다. Word 검토 메모로 숨기지 않는다.

| 자리 | 배치 위치 | 영역 안에 넣을 안내 문구 | 초기 크기 |
|---|---|---|---|
| S1 | 1단계 설명 다음 | 기준일자와 T1·T2 편집 대상 선택 화면 삽입 | 본문 폭, 높이 약 55~65mm |
| S2 | 2단계 설명 다음 | 운항편·여객 현황과 시간대별 여객수 조정 화면 삽입 | 본문 폭, 높이 약 80~90mm |
| S3 | 3단계 설명 다음 | 아일랜드·부스 선택과 운영 조건 편집 화면 삽입 | 본문 폭, 높이 약 80~90mm |
| S4 | 4단계 설명 다음 | 출국장 선택과 운영시간·시설 수량 편집 화면 삽입 | 본문 폭, 높이 약 80~90mm |

- 본문 폭은 참고 문서 기준 약 160mm이며, 공간의 높이는 임시 치수다. 최종 조판 시 설명과 그림이 읽기 좋게 조정한다.
- 각 공간에 참고 양식의 캡션 스타일로 `그림 1`부터 순서대로 화면명을 붙인다.
- 테두리는 간결하게 처리하고, 안내 문구는 작은 회색 글씨 한 줄로 둔다.
- 안내 문구와 캡션·삽입 공간이 페이지 경계에서 분리되지 않게 배치한다.
- 출국장·체크인 편집부까지 포함할 수 있도록 화면 공간을 확보한다. 읽기 어려운 전체 화면을 억지로 한 자리에 축소하도록 요구하지 않는다.
- 최초 조판 목표는 목차를 포함해 약 6~8쪽으로 잡되, 화면 공간 확보와 가독성을 우선한다. 4단계를 반드시 4쪽에 맞추지는 않는다.

## 5. 참고 문서 서식 적용

계획 단계에서 DOCX 내부 XML을 읽어 아래 사항을 확인했다. 실제 렌더링 및 시각 검증은 아직 수행하지 않았으며, 본문 글꼴의 상속값 등 세부 사항은 제작 단계에서 확정한다.

| 항목 | 확인 내용 및 적용 방침 |
|---|---|
| 용지 | A4 세로, 약 210 × 297mm |
| 여백 | 왼쪽 약 30mm, 오른쪽·위·아래 약 20mm |
| 구역 | 원본 1개 구역. 별첨도 같은 용지·여백을 기본으로 사용 |
| 머리말 | 사업명과 문서명. 사업명 형식을 유지하고 문서명을 별첨 제목으로 변경 |
| 바닥글 | `- 쪽번호 -` 형식 재사용 |
| 본문 | `PMBody` 등 원본의 스타일과 상속 구조 재사용 |
| 제목 | `PMHeading1`·`PMHeading2`·`PMHeading3` 및 번호 체계 재사용 |
| 캡션 | `PMCaption` 재사용 |
| 목차 | `PMTocTitle`·`PMToc` 등 원본 목차 형식 재사용 |

원본을 보존하고 복사본을 별첨으로 편집한다. 기존 승객예고 내용·용어표·그림·목차 항목은 신규 별첨 내용으로 교체하며, 기존 주제에 속한 본문이나 그림이 남지 않게 확인한다. 다른 디자인 프리셋을 덧씌우지 않는다.

참고 문서의 현재 SHA-256은 `941E091935FF6A32A7EA08FF85B1052D16A23CB6A658B775F7ACAA0513A973A8`이다. 제작 전후에 원본이 변경되지 않았는지 확인한다. 메타데이터의 페이지 수는 실제 렌더링 페이지 수로 간주하지 않는다.

## 6. 기능 근거와 표현 주의사항

| 근거 위치 (`react/src/modules/pm/pages/userSmlt/` 기준) | 확인할 내용 |
|---|---|
| `UserSmltConfig.tsx` | 날짜 조회, 현재상태 저장, 실행 확인 및 모니터링 이동 |
| `components/TerminalIntro.tsx` | 터미널 편집 대상 선택과 전체 실행 범위 |
| `components/SmltGnb.tsx` | 기준일자·현재상태 저장·시뮬레이션 실행의 실제 명칭 |
| `tabs/flightPax/` | 현황 표시, 전체·시간대별 비율, 운항편 수 유지 |
| `tabs/checkinCounter/` | 아일랜드·부스·항공사·운영시간·기기 수량 편집 |
| `tabs/departure/` | 출국장 사용 여부·운영시간·레인·보안검색대 수량 편집 |

- 현재상태 저장과 시뮬레이션 실행은 구분하되, 단계마다 수동 저장이 필수라고 쓰지 않는다.
- 편집부의 `적용`을 누르지 않으면 실행에 반영되지 않는다고 단정하지 않는다. 현재 구현은 실행 시 편집 중인 조건도 수집한다.
- 설정 화면의 현황·조정값을 시뮬레이션 계산 완료 후의 결과로 표현하지 않는다.
- 기준 조건으로 운영자료 또는 저장 조건을 이용한다는 정도로 설명한다. 과거 문서의 폐지된 편집 ID·회차·별도 셀프체크인 탭을 현재 기능으로 소개하지 않는다.
- 공항 실운영에 즉시 반영하는 기능처럼 표현하지 않는다. 문서의 대상은 사용자 시뮬레이션 조건 설정 및 예측 검토다.

## 7. 후속 제작 순서

1. 원본 서식 조사: `documents` 스킬의 템플릿 절차에 따라 원본을 렌더링하고 구역·스타일·목차·머리말·바닥글을 확인한다. 작업용 임시 폴더의 `artifact.md`에 재사용할 서식과 교체 범위를 기록한다.
2. 원고 작성: 확정된 독자와 범위에 맞춰 개요, 4단계 설명, 실행 이후 요약을 작성한다. 실제 버튼·항목 명칭과 대조한다.
3. DOCX 신규 생성: 원본 복사본에 원고와 S1~S4 공간을 배치하고 제목·목차·캡션·쪽번호를 정리한다. 제작 시작 시 스킬의 산출물 작업 시작 절차를 수행한다.
4. 서식·구조 확인: 원본에서 유지할 스타일과 문서 구성요소를 대조하고, 기존 승객예고 내용의 잔존 여부 및 목차·번호 참조를 검사한다. Word 필드 갱신이 불가하면 열 때 갱신하도록 설정하고 제한을 기록한다.
5. 시각 검증: `render_docx.py`로 전 페이지를 PNG로 렌더링한 뒤 각 페이지를 확인한다. 글자 누락·잘림·중첩·캡션 분리·공간 부족·불필요한 빈 페이지를 수정하고 다시 검증한다.
6. 결과 제공: 최종 DOCX 한 개를 제공한다. 검증용 PNG·PDF·임시 스크립트는 납품물에 포함하지 않는다.

문서 제작은 스킬이 지정하는 작업공간 런타임·의존성을 사용한다. 렌더러 환경 문제는 실제로 확인한 뒤 처리한다. LibreOffice 부재로 렌더링할 수 없는 경우에는 구조 검사를 수행하고 시각 검증 미완료를 명시하며, 시각 검증을 통과한 것으로 보고하지 않는다.

## 8. 완료 및 검증 기준

### 현재 계획 작업

- 이 계획 파일에 요구사항, 인터뷰 확정 사항, 4단계 구성, 화면 자리, 후속 제작·검증 방법을 기록한다.
- 변경 diff와 공백 오류를 확인한다.
- 문서만 변경하므로 React 타입 검사·lint·빌드·도메인 회귀검사는 실행하지 않는다.

### 후속 DOCX 작업

- 지정한 파일명으로 새 문서를 생성하고 원본은 변경하지 않는다.
- 사업·검토 담당자가 사용자 시뮬레이션의 목적과 설정 범위를 이해할 수 있다.
- 설명이 요청한 4단계로 구성되며, 실행·모니터링·결과 확인은 간결하게 정리된다.
- 가상 시나리오·수치 예시·검증하지 않은 결과를 넣지 않는다.
- S1~S4에 실제 화면을 넣을 공간과 짧은 안내 문구가 있다.
- 참고 문서의 서식과 일관되고, 전 페이지 렌더링 검증을 마친다. 수행하지 못한 검증은 사유를 구분해 보고한다.
