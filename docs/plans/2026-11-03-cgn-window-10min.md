# 혼잡등급 · 혼잡해소 관측구간을 직전 10분으로 축소

작성일: 2026-11-03 · 대상: `java/cast/domains`, `java/cast/service/impl`, `react/src` · 상태: **구현 (참조 사본, 실제 백엔드 빌드 대기)**

`java/`는 참조 사본이라 이 저장소에서 컴파일하지 않는다. 실제 백엔드 빌드는 별도로 한다.

---

## 1. 배경

혼잡등급 판정값 W(t)는 평가시각 직전 30분 `[t−30, t)` 처리 여객의 가중평균 대기시간이었다(2026-10-24).
산출 과정을 단순화하려고 **조회 시각의 스냅샷**, 곧 결과 시각 t 의 10분 행 하나로 판정한다.

- 결과 시각은 구간 끝이라 t 의 스냅샷은 `[t−10, t)` 10분 행이다. 출국장은 CAST 가 시각 t 에 준 `AVG_WTNG_HR` 와 같은 값이다.
- 요약보기 상단 요약정보의 평균 대기시간(`FcltWtngIntrvl`)과 피크시간도 이미 같은 정의다.

## 2. 확정한 결정

| 항목 | 결정 |
|---|---|
| 판정값 W(t) | `[t−10, t)` 처리 여객의 처리인원 가중평균 대기시간 = 그 행의 `WTNG_PSEC_SUM / PRCS_PSG_CNT` |
| 적용 범위 | 등급뿐 아니라 혼잡해소 판정 · 예측 이동평균 창 · 추천의 λ·μ·Q0·s 관측구간까지 **모두 10분** |
| 구현 | `QueueWaitWindow.WINDOW_MIN` 30 → 10. `FcltWtngDay` · `WaitAvgForecast` · `FacilityQueueCalculator` 는 이 상수와 구간 길이만 따른다 |
| 바꾸지 않는 것 | 목표 해소시간 기본값 30분(`DFLT_TARGET_MIN`), 혼잡해소 게이지 `max(30 − 해소분, 0) / 30`, 등급 기준표, 지표 4종 · 차트의 30분 슬롯 |
| API 계약 | 바꾸지 않는다. 필드 의미(관측구간 길이)만 달라진다 |

등급만 10분으로 바꾸면 카드 등급은 BUSY 인데 해소는 "이미 해소(0분)"처럼 어긋나서 한 상수로 묶었다.

## 3. 바뀌는 화면 값

| 화면 요소 | 이전 | 이후 |
|---|---|---|
| 요약보기 카드 · 칩 등급, `cgnWtngSec`, 카드 정렬, 터미널 대표 등급 | 직전 30분 | 직전 10분 |
| 카드 처리율(시간당 환산) · 부하율 · 해소 시각 · 추천 수량 | 직전 30분 관측 | 직전 10분 관측 |
| 맵형태보기 · 출국장 · 체크인 상세의 등급 · 추천 · 해소 | 직전 30분 | 직전 10분 |
| 혼잡해소 팝업 관측구간 · 평균 대기 · λ · μ · 예측 평균 창 | 30분 | 10분 |
| 지표 4종 · 차트 (슬롯 `[hhmm, hhmm+30)`) | — | 변화 없음 |

## 4. 관측 조건

- 체크인: 직전 10분 행 1개가 있고 관측(`OBSRVN_YN = Y`)이며 처리 여객 전원의 대기시간이 있어야 한다.
- 출국장: 결과 시각 `t−10`, `t` 두 개가 터미널에 있어야 한다(이전 네 개).
- 하루 첫 10분에 전날 결과가 없으면 산정 불가다(이전 첫 30분).

## 5. 감수하는 점

- 10분 표본이라 처리 여객이 적은 시간대에는 한두 명이 등급을 바꿔 10분마다 오르내릴 수 있다.
- 10분 동안 처리 0명이면 산정 불가(회색)다. 30분보다 자주 나온다.
- λ·μ 가 10분에서 나와 추천 수량 · 해소 시각도 30분 때보다 출렁인다.

## 6. 검증

- 프런트: `npx tsc -b` · `npx eslint` · 목업(`QUEUE_OBS_MIN = 10`)으로 팝업 관측구간 · 예측 창 표기 확인
- 백엔드: 실제 레포 빌드 후 같은 `smltId` · 터미널 · `hhmm` 에서
  - 카드 `cgnWtngSec` = 해당 시설 `TN_PM_SMLT_FCLT_WTNG_RSLT` 의 `SEC_BGNG_DT = t−10` 행 `WTNG_PSEC_SUM / PRCS_PSG_CNT`
  - 카드 · 맵 · 체크인 상세 · 팝업의 등급 · `reqCnt` · 해소 시각이 서로 같은지
